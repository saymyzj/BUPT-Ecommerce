# 《Web 后端开发技术》期末大作业分工指南

## 1. 项目基本信息

- 选题：题目一，AI 驱动的“高并发秒杀与智能电商”后台系统
- 团队规模：3 人
- API 调试工具：Apifox
- 前端要求：只做简单测试页面，用于辅助登录、秒杀、接收推送、AI 咨询等核心链路验证
- 远程仓库：[saymyzj/BUPT-Ecommerce](https://github.com/saymyzj/BUPT-Ecommerce)

本项目采用“人负责决策与文档，AI 负责代码生成与样板实现”的开发方式。代码量不是主要分工依据，主要分工依据是架构责任、模块边界、接口契约、核心链路和最终验收。

## 2. 作业要求拆解

根据指导书，本项目最终需要交付：

1. 作业报告
2. 完整源代码工程
3. Apifox 导出文件
4. 3-5 分钟演示视频

评分重点包括：

| 评分项 | 占比 | 本项目应对方式 |
| --- | ---: | --- |
| 系统开发实现 | 50% | 至少 3 个独立服务，真实使用 MySQL、Redis、MQ、Gateway，提供 Swagger/OpenAPI |
| 测试配置与演示视频 | 10% | 提供 Apifox 测试集合，录制核心链路演示视频 |
| 架构设计与生产环境演进说明 | 40% | 重点写清楚本地架构、时序图、ER 图、技术选型依据、高可用、高并发扩容和 AI 调用优化 |

本项目的高分关键不是 CRUD，而是以下核心架构链路：

```text
客户端请求
-> API Gateway 统一入口
-> 秒杀服务使用 Redis 原子扣减库存
-> 扣减成功后投递 MQ
-> 订单服务异步消费并落库
-> 订单创建成功后通过 SSE/WebSocket 推送结果
-> AI 服务提供商品咨询和购买建议
```

## 3. 总体架构方案

建议本地原型拆分为以下服务：

| 服务 | 主要职责 | 负责人 |
| --- | --- | --- |
| gateway-service | 统一入口、路由、JWT 校验、基础限流 | 成员 A |
| user-service | 注册、登录、角色权限、JWT 签发、注销登录 | 成员 A |
| product-seckill-service | 商品管理、库存管理、秒杀活动、Redis 预热、原子扣库存 | 成员 B |
| order-service | MQ 消费、订单落库、订单状态查询、幂等控制 | 成员 B |
| ai-service | 商品咨询、商品上下文构造、LLM 调用、AI 缓存与降级 | 成员 C |
| push-service 或推送模块 | SSE/WebSocket 推送订单创建结果 | 成员 C |
| simple-test-page | 简单前端测试页 | 成员 C |

如果时间紧张，可以把 `push-service` 合并进 `order-service`，但文档中仍需要把“订单创建”和“实时推送”的职责讲清楚。


### 6.5 Redis 设计要求

建议统一 Redis key：

```text
seckill:stock:{activityId}
seckill:user:{activityId}:{userId}
seckill:result:{activityId}:{userId}
seckill:activity:{activityId}
```

含义：

| Key | 含义 |
| --- | --- |
| `seckill:stock:{activityId}` | 秒杀活动库存 |
| `seckill:user:{activityId}:{userId}` | 用户是否已经参与该活动 |
| `seckill:result:{activityId}:{userId}` | 用户秒杀结果 |
| `seckill:activity:{activityId}` | 活动基础信息缓存 |

Redis 扣库存必须是原子操作。推荐使用 Lua 脚本完成：

1. 判断活动是否存在
2. 判断用户是否重复抢购
3. 判断库存是否大于 0
4. 扣减库存
5. 写入用户抢购标记
6. 返回扣减结果

禁止在高并发秒杀接口中直接 `UPDATE database SET stock = stock - 1`。

### 6.6 MQ 设计要求

推荐 RabbitMQ。

建议消息流：

```text
seckill.order.exchange
-> seckill.order.create.queue
-> order-service
```

Routing key：

```text
seckill.order.create
```

订单创建消息格式：

```json
{
  "messageId": "uuid",
  "eventType": "SECKILL_ORDER_CREATE",
  "activityId": 1,
  "userId": 10001,
  "productId": 20001,
  "quantity": 1,
  "createdAt": "2026-05-24T20:00:00"
}
```

成员 B 必须保证消费端幂等。推荐方式：

1. `messageId` 建唯一索引或消费记录表
2. `activityId + userId` 建唯一索引，防止重复订单
3. 消费失败时重试
4. 多次失败进入死信队列
5. 文档中说明补偿任务如何处理异常订单

### 6.7 秒杀接口行为

秒杀请求成功扣减 Redis 后，接口不要同步创建订单，应立即返回：

```json
{
  "code": 0,
  "message": "queued",
  "data": {
    "activityId": 1,
    "status": "QUEUEING"
  }
}
```

订单真正创建成功后，再通过 SSE 或 WebSocket 推送给用户。

### 7.5 AI 智能导购要求

AI 咨询接口建议：

```text
POST /api/ai/products/{productId}/consult
```

请求示例：

```json
{
  "question": "这款商品适合学生党购买吗？"
}
```

服务端处理流程：

```text
查询商品信息
-> 拼接商品上下文和用户问题
-> 检查相似问题缓存
-> 调用 LLM API
-> 返回购买建议
```

AI 缓存 key 建议：

```text
ai:product:qa:{productId}:{questionHash}
```

文档中必须说明生产环境优化：

1. 热门商品问答缓存
2. 相似问题复用
3. 用户级限流
4. 请求队列
5. 超时降级
6. LLM API 失败时返回兜底建议

### 7.6 实时推送要求

推荐优先使用 SSE，因为本项目只需要服务端向客户端推送订单结果，SSE 比 WebSocket 更简单、稳定、易演示。

推送事件建议：

```json
{
  "eventType": "ORDER_CREATED",
  "activityId": 1,
  "orderId": 90001,
  "userId": 10001,
  "status": "CREATED",
  "message": "订单创建成功"
}
```

简单测试页面至少支持：

1. 登录并保存 Token
2. 连接 SSE 或 WebSocket
3. 发起秒杀请求
4. 显示“排队中”
5. 收到订单创建成功推送
6. 输入商品问题并显示 AI 回答

## 8. 统一接口规范

所有服务响应必须统一：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

推荐错误码：

| code | 含义 |
| ---: | --- |
| 0 | 成功 |
| 400 | 请求参数错误 |
| 401 | 未登录或 Token 无效 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 409 | 业务冲突，例如重复秒杀 |
| 429 | 请求过于频繁 |
| 500 | 服务器内部错误 |
| 10001 | 库存不足 |
| 10002 | 秒杀活动未开始 |
| 10003 | 秒杀活动已结束 |
| 10004 | 用户已参与该活动 |
| 20001 | MQ 投递失败 |
| 30001 | AI 服务暂不可用 |

分页响应建议：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "records": [],
    "page": 1,
    "pageSize": 10,
    "total": 100
  }
}
```

### 12.3 日常开发流程

```bash
git checkout dev

```

开发完成后：


### 12.4 Commit 信息规范

使用以下前缀：

| 前缀 | 含义 |
| --- | --- |
| `feat:` | 新功能 |
| `fix:` | 修复问题 |
| `docs:` | 文档 |
| `refactor:` | 重构 |
| `test:` | 测试 |
| `chore:` | 配置、依赖、构建脚本 |

示例：

```text
docs: add team role guide

feat: add redis lua seckill stock deduction
```

### 12.5 Pull Request 规范

合并前必须满足：

### 12.6 冲突处理规则

出现冲突时：

1. 先确认冲突文件属于谁负责
2. 不允许直接覆盖他人代码
3. 涉及接口契约、数据库表、Redis key、MQ 消息格式的冲突，必须由成员 A 统一裁定
4. 解决冲突后必须重新跑相关接口测试

### 12.7 禁止事项

禁止：

1. 直接向 `main` 推送
2. 未更新文档就修改接口契约
3. 私自修改他人负责模块的数据库字段
4. 私自修改 Redis key 命名
5. 私自修改 MQ 消息格式
6. 把密钥、Token、LLM API Key 提交到仓库
7. 提交无关 IDE 缓存、日志、临时文件

## 19. 本项目的工作原则

1. 先文档，后代码。
2. 先契约，后实现。
3. 先核心链路，后边缘功能。
4. CRUD 可以交给 AI 快速生成，但架构决策必须由人确认。
5. 所有跨服务交互必须写入文档。
6. 成员 A 对接口契约和最终联调拥有最终裁定权。
7. 成员 B 对秒杀、Redis、MQ、订单一致性负责。
8. 成员 C 对 AI、推送、Apifox、测试页面和演示体验负责。
9. 最终目标不是堆功能，而是证明系统具备高并发、异步削峰、实时反馈和 AI 集成能力。
