# 生产环境演进方案

## 1. 目标

本文档用于说明本地原型如何演进到更接近生产环境的部署形态，重点服务于课程报告和答辩说明。

## 2. 当前形态

当前阶段采用单机或轻量化本地原型部署，重点验证以下能力：

1. 统一入口
2. 高并发秒杀
3. 异步削峰
4. 实时推送
5. AI 咨询

## 3. 演进方向总览

| 能力 | 本地原型 | 生产演进 |
| --- | --- | --- |
| Gateway | 单实例 | 多实例 + 前置负载均衡 |
| 微服务 | 单实例 | 水平扩容 |
| Redis | 单机 | Sentinel / Cluster |
| RabbitMQ | 单机 | 集群化 |
| MySQL | 单机 | 主从复制、读写分离 |
| 秒杀库存 | 单点库存 | 热点分片、预热、限流 |
| 订单创建 | 同步不可行 | MQ 异步削峰 |
| 推送 | 简单 SSE | 独立推送服务或网关长连接治理 |
| AI 调用 | 直连 | 缓存、限流、排队、降级 |

## 4. Gateway 演进

### 4.1 多实例部署

Gateway 不应成为单点故障。生产环境应至少部署多个实例，并放在 Nginx 或云负载均衡之后。

### 4.2 网关职责收敛

Gateway 只保留：

1. 路由
2. 鉴权
3. 限流
4. 跨域
5. 日志

业务逻辑不下沉到网关。

## 5. 微服务扩容

### 5.1 水平扩容

商品、秒杀、订单、AI、推送服务都可以按实例数扩容。

### 5.2 状态外置

服务尽量保持无状态，状态沉淀到：

1. MySQL
2. Redis
3. MQ

这样才能支持横向扩展。

## 6. Redis 演进

### 6.1 单机到 Sentinel

适用于先提升可用性，解决单点故障。

### 6.2 Sentinel 到 Cluster

适用于进一步扩展容量与分片能力，支撑热点秒杀库存和高并发读写。

### 6.3 热点库存治理

秒杀库存属于热点数据，生产环境需要：

1. 预热库存
2. 热点 key 保护
3. 限流与熔断
4. 必要时做库存分片

## 7. RabbitMQ 演进

### 7.1 单机到集群

订单创建消息、业务事件消息必须具备高可用能力，避免单点宕机导致消息丢失。

### 7.2 消息可靠性

生产环境应重点覆盖：

1. 消息持久化
2. 生产者确认
3. 消费者确认
4. 重试机制
5. 死信队列

## 8. MySQL 演进

### 8.1 主从复制

订单、商品、用户等核心表进入生产后，应考虑主从复制。

### 8.2 读写分离

查询类接口走读库，写操作走主库。

### 8.3 订单与秒杀表设计

必须保留：

1. 唯一索引
2. 幂等约束
3. 状态字段
4. 审计字段

## 9. 秒杀链路演进

### 9.1 直接写库不可取

高并发场景下直接扣数据库库存会导致：

1. 竞争锁冲突严重
2. 写放大
3. 超卖风险
4. 响应变慢

### 9.2 推荐路径

```text
请求进入 Gateway
 -> Redis 原子扣减
 -> MQ 异步创建订单
 -> 订单服务落库
 -> 推送结果
```

### 9.3 高并发扩展

生产环境可进一步引入：

1. 秒杀活动预热
2. 库存分片
3. 用户级限流
4. 熔断降级
5. 异步补偿任务

## 10. AI 调用演进

### 10.1 不能无限同步直连

原因包括：

1. 延迟不稳定
2. 成本不可控
3. 外部服务故障会放大本地故障
4. 高并发下容易拖垮主链路

### 10.2 生产级优化

建议引入：

1. 热门问题缓存
2. 相似问法复用
3. 请求排队
4. 用户级限流
5. 超时降级

## 11. 推送服务演进

若采用独立推送模块，生产环境应考虑：

1. 长连接资源管理
2. 连接心跳
3. 断线重连
4. 推送事件幂等
5. 消息重放策略

## 12. 可观测性

生产环境必须补充：

1. 日志
2. 指标
3. 链路追踪
4. 告警

否则无法证明高并发链路的稳定性。

## 13. 报告写法建议

最终报告建议围绕以下逻辑展开：

1. 为什么要拆服务
2. 为什么要统一入口
3. 为什么秒杀要走 Redis + MQ
4. 为什么订单要异步化
5. 为什么 AI 要缓存和降级
6. 如何从本地原型演进到生产环境
