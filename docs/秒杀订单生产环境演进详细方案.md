# 秒杀订单生产环境演进详细方案

## 1. 文档目标

本文档是成员 B 对 `docs/生产环境演进方案.md` 的细化补充，专门说明秒杀与订单链路在正式生产环境中如何改造部署。

作业要求明确指出：本地原型能跑通只是第一步，报告中必须说明百万日活场景下如何解决高可用、高并发扩容和 AI 调用优化。本文档用于支撑最终报告中的“正式生产环境演进方案”章节。

本文档不改变本地原型接口契约，不新增公开 API，不修改 Gateway、JWT、权限规则。

## 2. 本地原型与生产环境差异

| 能力 | 本地原型 | 正式生产环境 |
| --- | --- | --- |
| Gateway | 单实例 | 多实例 + 负载均衡 |
| 秒杀服务 | 单实例 | 多实例水平扩容 |
| 订单服务 | 单实例消费者 | 多实例消费者组 |
| Redis | 单机 | Sentinel 或 Cluster |
| RabbitMQ | 单机 | 集群 + 持久化 + 死信 |
| MySQL | 单机 | 主从复制、读写分离、备份恢复 |
| 秒杀库存 | 单个库存 key | 预热、热点保护、必要时库存分片 |
| 消息可靠性 | 投递失败回滚 Redis | Outbox/本地消息表 + 补偿任务 |
| 监控 | 控制台和管理台观察 | 指标、日志、链路追踪、告警 |

## 3. 高可用设计

高可用的目标是：任意单个节点故障时，系统仍能提供服务，或者可以快速恢复。

### 3.1 Gateway 与服务实例

Gateway 集群由成员 A 负责整体设计，成员 B 的秒杀与订单服务需要适配多实例部署。

生产部署形态：

```text
Nginx/SLB
 -> Gateway 集群
 -> product-seckill-service 多实例
 -> order-service 多实例
```

秒杀服务和订单服务必须尽量无状态：

1. 不在 JVM 内存中保存秒杀库存。
2. 不在本地文件中保存订单状态。
3. 状态统一放到 MySQL、Redis、RabbitMQ。
4. 任意实例重启后，不影响其他实例继续处理请求。

### 3.2 Redis 高可用

本地原型使用单机 Redis。生产环境建议分两阶段演进：

| 阶段 | 方案 | 解决问题 |
| --- | --- | --- |
| 第一阶段 | Redis Sentinel | 主从复制、主节点故障自动切换 |
| 第二阶段 | Redis Cluster | 更大容量、更高并发、数据分片 |

秒杀库存属于热点数据，Redis 需要重点保护：

1. 活动开始前预热库存和活动信息。
2. 对热点活动 key 设置合理 TTL。
3. 对售罄活动设置“售罄标记”，减少无意义扣减。
4. 必要时对单活动库存进行分片。

### 3.3 RabbitMQ 高可用

本地原型使用单机 RabbitMQ。生产环境应使用 RabbitMQ 集群。

关键设计：

1. Exchange、Queue、消息都开启持久化。
2. 生产者启用确认机制，确认消息是否真正到达 Broker。
3. 消费者手动 ACK，订单落库成功后再确认。
4. 消费失败多次后进入死信队列。
5. 死信队列必须有告警和人工处理流程。

### 3.4 MySQL 高可用

本地原型使用单机 MySQL。生产环境至少需要：

1. 主从复制。
2. 定期备份。
3. 读写分离。
4. 慢 SQL 监控。
5. 订单表按时间或订单号扩展分表的预留方案。

订单写入必须走主库；订单查询可以走从库。

## 4. 高并发扩容策略

### 4.1 流量入口削峰

高并发秒杀开始前，入口层要先过滤异常流量：

1. Gateway 层做用户级、IP 级限流。
2. 活动未开始时直接返回 `10002`，不进入扣库存逻辑。
3. 活动已售罄时快速失败，减少 Redis 和 MQ 压力。
4. 对恶意重复请求进行封禁或降级。

成员 B 不实现 Gateway 限流，但需要在报告中说明秒杀服务依赖 Gateway 入口保护。

### 4.2 秒杀服务扩容

`product-seckill-service` 可以多实例部署。

扩容依据：

| 指标 | 含义 | 处理方式 |
| --- | --- | --- |
| QPS 持续升高 | 请求量变大 | 增加秒杀服务实例 |
| CPU 使用率高 | 业务处理压力大 | 增加实例或优化 Lua 调用 |
| Redis 响应变慢 | Redis 成为瓶颈 | 热点 key 保护或库存分片 |
| 错误率升高 | 系统过载 | 限流、熔断、降级 |

### 4.3 库存分片

本地原型使用：

```text
seckill:stock:{activityId}
```

生产环境如果单个 key 过热，可以拆分为多个库存桶：

```text
seckill:stock:{activityId}:shard:0
seckill:stock:{activityId}:shard:1
seckill:stock:{activityId}:shard:2
...
```

请求进入后按用户 ID 或随机策略选择一个分片扣减。

库存分片需要保证：

1. 所有分片库存总和等于活动库存。
2. 每个分片仍使用 Lua 原子扣减。
3. 分片扣完后可以尝试其他分片，但尝试次数要有限，避免拖慢接口。
4. 所有成功扣减总数不能超过活动库存。

本地原型不实现库存分片，只在生产演进中说明。

### 4.4 MQ 队列削峰

秒杀请求可能瞬间到达，但订单创建可以慢慢处理。

RabbitMQ 的作用是：

```text
前面快速接收抢购请求
后面按订单服务处理能力逐步落库
```

如果队列积压：

1. 扩容 `order-service` 消费实例。
2. 检查 MySQL 是否成为写入瓶颈。
3. 如果 MySQL 压力过大，限制订单消费速度，保护数据库。
4. 对失败消息进入死信队列。

## 5. 数据一致性演进

### 5.1 本地原型一致性

本地原型链路：

```text
Redis 扣减成功
-> 发布 MQ
-> order-service 消费
-> MySQL 落库
-> Redis 结果更新
```

本地原型中，如果 Redis 扣减成功但 MQ 投递失败，采用 Redis 回滚：

```text
库存加回去
删除用户参与标记
结果写为 FAILED
返回 20001 MQ 投递失败
```

这种方案适合本地演示，清晰直观。

### 5.2 生产环境 Outbox 方案

生产环境不能只依赖接口线程回滚。推荐升级为 Outbox，也叫本地消息表方案。

通俗理解：

```text
先把“我要发 MQ 消息”这件事可靠地写进数据库，
再由后台任务慢慢把消息发到 MQ。
```

推荐流程：

```text
Redis 扣减成功
-> 写本地消息表，状态为 PENDING
-> 后台任务扫描 PENDING 消息
-> 发布 RabbitMQ
-> 发布成功后改为 SENT
-> 发布失败继续重试
```

好处：

1. MQ 短暂不可用时，消息不会直接丢失。
2. 可以通过后台任务持续重试。
3. 可以监控未发送消息数量。
4. 可以人工补偿异常消息。

### 5.3 订单消费幂等

生产环境必须假设 MQ 可能重复投递。

幂等保障：

1. `mq_message_logs.message_id` 唯一，防止同一消息重复处理。
2. `orders.order_no` 唯一，防止同一订单号重复落库。
3. `orders(user_id, activity_id)` 唯一，防止同一用户同一活动重复下单。

即使消息重复消费多次，最终也只能创建一笔订单。

## 6. 故障处理方案

| 故障 | 影响 | 生产处理 |
| --- | --- | --- |
| Redis 单节点故障 | 秒杀扣减不可用 | Sentinel/Cluster 自动切换 |
| Redis 响应变慢 | 秒杀接口变慢 | 热点 key 保护、库存分片、限流 |
| MQ 不可用 | 订单消息无法投递 | Outbox 记录消息，后台重试 |
| MQ 消息积压 | 订单创建延迟 | 扩容订单服务，保护 MySQL |
| order-service 宕机 | 队列消息暂不消费 | 重启或扩容消费者，消息仍在 MQ |
| MySQL 写入失败 | 订单无法落库 | MQ 重试，失败进入死信 |
| 重复消费 | 可能重复订单 | 幂等表和唯一索引兜底 |
| 死信消息堆积 | 部分订单失败 | 告警，人工或补偿任务处理 |
| 推送失败 | 用户收不到通知 | 订单以 MySQL 为准，用户可查询结果 |

## 7. 监控与告警

生产环境必须能观察核心链路是否健康。

### 7.1 Redis 监控

| 指标 | 含义 | 异常说明 |
| --- | --- | --- |
| Redis QPS | Redis 请求量 | 秒杀活动是否过热 |
| Redis 延迟 | 命令响应时间 | Redis 是否成为瓶颈 |
| 库存 key 剩余值 | 活动剩余库存 | 是否出现负数 |
| Lua 执行失败数 | 扣减失败 | 脚本或数据异常 |

### 7.2 RabbitMQ 监控

| 指标 | 含义 | 异常说明 |
| --- | --- | --- |
| 队列积压数 | 未消费消息数量 | 订单服务处理不过来 |
| 消费速率 | 每秒消费数 | 消费能力是否足够 |
| 死信数量 | 失败消息数量 | 订单创建异常 |
| ACK/NACK 数 | 消费确认情况 | 消费是否稳定 |

### 7.3 MySQL 监控

| 指标 | 含义 | 异常说明 |
| --- | --- | --- |
| 订单写入耗时 | 创建订单速度 | 数据库是否成为瓶颈 |
| 慢 SQL 数 | 慢查询数量 | 索引或 SQL 问题 |
| 主从延迟 | 从库落后时间 | 查询结果可能不新 |
| 唯一索引冲突数 | 重复请求数量 | 是否有重复消费或重复抢购 |

### 7.4 业务监控

| 指标 | 含义 |
| --- | --- |
| 秒杀请求数 | 活动流量规模 |
| 排队成功数 | Redis 扣减成功数量 |
| 订单创建成功数 | MySQL 最终成功订单 |
| 订单创建失败数 | 失败或死信订单 |
| 库存不足返回数 | 商品售罄情况 |
| 重复抢购返回数 | 用户重复点击情况 |

## 8. AI 调用生产优化边界

AI 咨询不是秒杀主链路，不能拖慢秒杀下单。

成员 B 负责提供商品上下文：

1. 商品名称。
2. 商品描述。
3. 原价。
4. 秒杀价。
5. 活动状态。

成员 C 负责 LLM 调用，但生产环境建议：

1. 热门商品问答缓存。
2. 相似问题复用。
3. 用户级限流。
4. 请求排队。
5. 超时降级。
6. LLM 故障时返回兜底建议。

AI 失败不能影响：

1. Redis 库存扣减。
2. MQ 下单。
3. 订单落库。

## 9. 报告可复用结论

最终报告中可以这样概括成员 B 的生产演进方案：

```text
本地原型通过 Redis Lua 原子扣减和 RabbitMQ 异步订单削峰完成高并发秒杀链路验证。生产环境中，秒杀服务和订单服务将以无状态多实例部署，Redis 从单机演进为 Sentinel 或 Cluster，RabbitMQ 从单机演进为集群并启用持久化、确认和死信队列，MySQL 采用主从复制、读写分离和备份恢复。为解决 Redis 扣减成功但 MQ 投递失败的问题，生产环境引入 Outbox 本地消息表和补偿任务，配合订单唯一索引和消息幂等表保证最终一致性。
```
