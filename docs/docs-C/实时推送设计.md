# 实时推送设计

## 1. 目标

实时推送用于通知普通用户自己的秒杀订单创建结果。推送不能静态展示，也不能在秒杀接口同步返回最终订单状态；必须由订单链路落库后触发。

## 2. 接口契约

订阅接口：

```text
GET /api/push/orders/subscribe
```

权限：

```text
CUSTOMER
```

鉴权：

```text
Authorization: Bearer <token>
```

Gateway 校验 token 后向 `push-service` 注入：

```text
X-User-Id
X-Username
X-User-Role
```

## 3. 技术选择

当前实现使用 SSE，原因：

1. 本项目只需要服务端向客户端推送订单结果。
2. SSE 易于演示和排查。
3. 浏览器可用 `fetch` 流式读取并携带 `Authorization` 请求头。

## 4. 当前实现链路

```text
用户登录
 -> 测试页携带 token 建立 SSE 连接
 -> Gateway 鉴权并注入 X-User-Id
 -> push-service 按 userId 保存 SseEmitter
 -> 用户发起秒杀
 -> product-seckill-service Redis 原子扣减
 -> RabbitMQ 投递订单创建消息
 -> order-service 消费 MQ 并落库
 -> order-service 写入 seckill:result:{activityId}:{userId}
 -> order-service 调用 push-service 内部发布接口
 -> push-service 只向该 userId 的连接发送 ORDER_CREATED
```

## 5. 推送事件

事件名：

```text
order-result
```

事件数据：

```json
{
  "eventType": "ORDER_CREATED",
  "activityId": 1,
  "orderId": 90001,
  "orderNo": "ORD202606040001",
  "userId": 10001,
  "status": "CREATED",
  "message": "订单创建成功"
}
```

外层仍使用统一响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

## 6. 避免写死结果的规则

1. 订阅成功只发送 `CONNECTED`，不发送订单成功。
2. 秒杀接口只显示 `QUEUEING`。
3. 测试页只有收到 `order-result` 后才能显示订单状态。
4. 测试页收到 `orderId` 后必须再调用订单详情接口验证。
5. 推送服务按 `userId` 投递事件，不能广播所有用户订单。

## 7. 验证步骤

1. 普通用户登录。
2. 建立 SSE 连接。
3. 清空测试页日志。
4. 发起秒杀，确认响应为 `queued`。
5. 等待 `ORDER_CREATED` 推送。
6. 使用推送中的 `orderId` 查询 `GET /api/orders/{orderId}`。
7. 确认订单详情中的 `userId`、`activityId`、`status` 与推送一致。

## 8. 推送失败兜底说明

推送只作为订单结果的实时到达通道，不作为唯一事实来源。如果浏览器断线、SSE 被关闭或推送服务临时不可用，演示和联调时按以下方式兜底：

1. 秒杀接口返回 `QUEUEING` 后，不直接宣称订单成功。
2. 优先等待 `ORDER_CREATED` 推送。
3. 如果指定时间内没有推送，调用 `GET /api/seckill/activities/{activityId}/result` 查询秒杀结果。
4. 如果结果中存在 `orderId`，继续调用 `GET /api/orders/{orderId}` 验证订单详情。
5. 最终以订单服务落库结果和订单详情接口为准，推送缺失只记录为实时通知链路异常。

该口径保证演示不会用静态推送或假订单结果冒充真实链路。

## 9. 已完成联调记录

2026-06-06 本地联调验证：

1. A、B 两个用户同时建立 SSE 连接时，A 用户发起真实秒杀订单后，仅 A 用户收到 `order-result / ORDER_CREATED`，B 用户未收到 A 的订单事件。
2. A 用户断开 SSE 后重新建立连接，再发起新的真实秒杀订单，重连后的 SSE 能继续收到 `ORDER_CREATED`。
