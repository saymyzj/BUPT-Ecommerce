# 第五周开发规划

> 版本：v1.1
> 核心调整：第五周首要任务不再是地图功能，而是修复数字人表现、问答准确性和语音播报体验。地图作为次要增强功能，在核心问题稳定后再接入；若时间不足，地图可以降级或暂缓，不影响主系统验收。

## 一、第五周总体目标

第五周的目标是让系统具备稳定、可信、可演示的最终状态。当前最影响演示效果的问题主要集中在数字人、问答能力和语音体验：

1. 数字人嘴型与语音不同步，视觉上容易出戏。
2. 数字人画面存在两重或重影问题，影响观感。
3. 问答回答不够精确，换一种问法后识别失败或答非所问。
4. 回答没有稳定语音，或语音生成太慢，影响数字人导览体验。
5. 当前数字人形象不够贴合景区文化特色，外观、服装、声音不方便配置。
6. 地图功能属于增强项，应排在数字人、问答和语音修复之后。

因此，第五周优先级调整为：

| 优先级 | 任务 | 定位 |
|---|---|---|
| P0 | 修复问答准确性和问法泛化能力 | 必须完成 |
| P0 | 修复数字人重影/两重显示问题 | 必须完成 |
| P0 | 补齐语音回答能力，整理高频回答预录语音 | 必须完成 |
| P1 | 优化数字人口型与语音表现 | 尽量完成 |
| P1 | 固定数字人播报姿态，避免错误口型造成观感问题 | 可作为兜底方案 |
| P1 | 增加数字人形象选择，支持外观、服装、声音配置 | 尽量完成 |
| P2 | 地图功能：游客端和后台端展示 | 由 A/B 完成 |

## 二、数字人修复规划

### 2.1 问题一：嘴型与语音对不上

当前问题：

- 数字人口型变化与语音节奏不一致。
- 用户能明显感觉“嘴在动，但不是在说当前这句话”。
- 如果继续强行保留不准确口型，反而会降低演示可信度。

处理方案：

1. 优先尝试修复口型同步逻辑。
2. 如果精细口型同步无法稳定完成，则采用兜底方案：数字人播报时保持较小幅度动作，避免明显错误口型。
3. 必要时可以让数字人处于相对固定姿态，只保留轻微表情或提示状态。
4. 语音播报时重点保证声音、字幕和回答内容正确，不再把不稳定口型作为强依赖。

验收标准：

- 播报时不能出现明显“嘴型乱动”的情况。
- 如果口型无法精准同步，数字人固定或轻微动作也可以接受。
- 语音结束后数字人必须停止说话状态，不能无声动嘴。

### 2.2 问题二：数字人有两重

当前问题：

- 页面中数字人存在两层叠加、重影或重复渲染。
- 可能是多个 canvas、video、模型容器或背景层重复显示。

处理方案：

1. 检查数字人组件是否重复挂载。
2. 检查页面切换、重新进入、播放状态变化时是否创建了多个实例。
3. 检查 canvas、video、透明背景、模型容器的层级和透明度。
4. 确保同一时间只存在一个数字人主显示层。
5. 在组件卸载或切换时释放旧实例，避免残留。

验收标准：

- 任意页面状态下只显示一个清晰的数字人。
- 切换页面、重新提问、停止播报、重播后不出现重影。
- 构建和演示环境中表现一致。

### 2.3 数字人兜底策略

如果第五周时间不足，不追求高精度口型，而采用稳定演示优先策略：

- 数字人固定站姿或坐姿。
- 播报时只显示“正在讲解/正在回答”的状态。
- 配合字幕、语音、轻微表情完成导览效果。
- 禁止出现错误嘴型、重复人像、无声动嘴。

这比“强行做不准的嘴型”更适合最终演示。

## 三、问答功能修复规划

### 3.1 当前问题

当前问答能力存在两个主要问题：

1. 回答不够精确，部分问题返回内容泛泛而谈。
2. 用户换一种问法后，系统识别不到原本应该命中的知识点。

例如：

- “门票多少钱？”
- “票价是多少？”
- “学生票怎么收费？”
- “买票贵不贵？”

这些问题语义接近，系统应该能识别为同一类票价问题，而不是只识别固定关键词。

### 3.2 修复方向

问答修复优先级高于地图。

主要修复方向：

1. 增加同义问法和改写问法测试集。
2. 对高频问题建立 FAQ 兜底规则。
3. 对票价、开放时间、路线、安全提示、拥挤避让、离线讲解等高风险问题优先保证准确。
4. 优化 RAG 检索逻辑，避免只靠关键词匹配。
5. 当知识库没有召回到可靠内容时，明确提示无法确定，不允许编造。
6. 回答中保留来源、置信度或命中依据，方便后台复盘。

### 3.3 问答测试集要求

第五周需要补充一组“换问法测试集”：

| 类型 | 要求 |
|---|---|
| 票价类 | 至少 10 种不同问法 |
| 开放时间类 | 至少 10 种不同问法 |
| 路线推荐类 | 至少 10 种不同问法 |
| 拥挤避让类 | 至少 10 种不同问法 |
| 安全提示类 | 至少 10 种不同问法 |
| 景点讲解类 | 至少 10 种不同问法 |

验收标准：

- 同义问法能够命中相同或相近答案。
- 高频问题不能答非所问。
- 高风险问题必须走 FAQ 或规则兜底。
- 问答准确率应达到 90% 以上。

## 四、语音回答与响应延迟规划

### 4.1 当前问题

当前语音交互存在两个风险：

1. 用户提问后只有文字回答，没有稳定语音播报。
2. 如果每次都实时生成语音，语音问答延迟可能过高，影响演示体验。

第五周需要把“能听到回答”和“响应不要太慢”作为核心体验要求。

### 4.2 目标要求

| 指标 | 要求 |
|---|---|
| 高频问题语音 | 使用预录或预生成语音，保证稳定播放 |
| 普通问题语音 | 可实时生成，但失败时文字回答不能受影响 |
| 语音问答延迟 | 建议控制在 5 秒以内 |
| 失败兜底 | 语音失败时显示明确提示，保留文字回答 |
| 演示稳定性 | 欢迎语、景点讲解、拥挤提醒、路线建议等必须可播报 |

### 4.3 怎么做到

建议采用“高频预录 + 实时生成 + 缓存兜底”的组合方案。

第一步，整理高频回答预录语音。

优先把演示中一定会问到、答案相对固定的问题整理出来，提前生成音频文件。这样用户提问命中这些问题时，后端直接返回音频地址，不用现场生成语音。

建议预录类型：

| 类型 | 示例 |
|---|---|
| 欢迎语 | 欢迎来到景区智能导览系统 |
| 景点介绍 | 主展馆、文化长廊、观景台等核心景点讲解 |
| 票价说明 | 门票价格、学生票、优惠说明 |
| 开放时间 | 开园、闭园、节假日说明 |
| 路线推荐 | 推荐游览路线、亲子路线、轻松路线 |
| 拥挤提醒 | 当前人流较多，建议错峰前往 |
| 异常提醒 | 当前景点暂不建议前往 |
| 兜底回答 | 暂时无法确认该问题，请咨询工作人员 |

预录语音文件建议放在后端静态媒体目录：

```text
media/tts/
```

命名建议：

```text
welcome.mp3
spot_main_hall_intro.mp3
ticket_price.mp3
open_time.mp3
crowd_warning.mp3
fallback_unknown.mp3
```

命中高频回答时，后端返回：

```json
{
  "answer": "主展馆展示景区核心文化内容，建议预留 30 分钟参观。",
  "audioUrl": "/media/tts/spot_main_hall_intro.mp3",
  "audioCached": true
}
```

第二步，普通问题实时生成语音并缓存。

非高频问题可以实时生成语音，但要设置超时和缓存：

```text
用户提问
 -> 后端生成文字回答
 -> 判断是否命中预录语音
 -> 命中：直接返回 audioUrl
 -> 未命中：调用 TTS 生成语音
 -> 生成成功：保存到缓存目录并返回 audioUrl
 -> 生成失败：只返回文字回答和语音失败提示
```

缓存 key 建议：

```text
tts:{answerHash}:{voiceId}
```

其中 `answerHash` 可以用回答文本的 SHA-256，避免同一回答重复生成语音。

第三步，前端文字和语音解耦。

前端不要等语音生成完才展示回答。推荐交互：

1. 1 秒内展示“正在思考”或首段文字。
2. 文字回答先出现。
3. 语音生成中显示“正在生成语音”。
4. 语音准备好后自动播放。
5. 超过 5 秒仍未生成，提示“语音生成较慢，请先查看文字回答”。

这样即使语音慢，也不会让用户长时间面对空白页面。

### 4.4 延迟控制手段

为了控制语音问答延迟：

1. 高频问题必须预录或预生成，不走实时 TTS。
2. 对相同回答启用音频缓存。
3. TTS 设置超时时间，例如 3 到 5 秒。
4. 前端文字和语音解耦，文字先返回，语音后播放。
5. 演示前预热缓存，提前访问高频问题。
6. 对欢迎语、景点讲解、拥挤提醒等演示必经语音，必须提前生成。

### 4.5 验收标准

| 验收项 | 通过标准 |
|---|---|
| 高频回答语音 | 高频问答能直接播放预录语音 |
| 普通回答语音 | 普通问题可生成语音或明确提示语音不可用 |
| 响应延迟 | 语音问答整体延迟尽量小于 5 秒 |
| 文字兜底 | 语音失败不影响文字回答 |
| 播放控制 | 支持停止当前播报，避免多个音频叠加 |

## 五、数字人形象管理规划

### 5.1 当前问题

当前数字人形象存在两个问题：

1. 形象比较固定，不够贴合景区文化特色。
2. 变装成本较高，短时间内不一定能做到真正的服装自由切换。

因此，第五周不建议强行做复杂换装系统，而是优先做“多形象选择”。

### 5.2 目标方案

数字人形象管理建议分两层：

1. 基础版：提供多个数字人形象供选择。
2. 增强版：支持配置外观、服装、声音、默认动作。

本期优先完成基础版。

### 5.3 多形象选择

如果当前数字人不好直接变装，可以准备多个形象资源，让管理员选择当前使用哪一个。

建议至少准备 2 到 3 类形象：

| 形象 | 定位 |
|---|---|
| 标准导游形象 | 默认讲解员，适合通用演示 |
| 景区文化形象 | 服装或配色贴近景区文化特色 |
| 亲和服务形象 | 更适合游客问答和温和提醒 |

前端或后台配置项建议：

```json
{
  "avatarId": "guide_classic",
  "displayName": "景区导览员",
  "voiceId": "female_warm",
  "style": "classic",
  "defaultExpression": "smile"
}
```

### 5.4 可配置内容

| 配置项 | 说明 |
|---|---|
| avatarId | 数字人形象 ID |
| displayName | 数字人名称 |
| outfitName | 服装或主题名称 |
| voiceId | 默认声音 |
| defaultExpression | 默认表情 |
| defaultMotion | 默认动作 |
| themeColor | 形象主题色 |
| enabled | 是否启用 |

如果服装不能单独切换，可以把不同服装做成不同 `avatarId`。

### 5.5 后台管理能力

后台可以增加“数字人形象管理”或“导览员配置”：

- 查看当前启用形象。
- 切换数字人形象。
- 切换默认声音。
- 设置默认表情和动作。
- 预览数字人。

本期不强制支持在线上传复杂模型，避免范围过大。

### 5.6 游客端展示规则

游客端只读取当前启用形象：

```text
GET /api/digital-human/config
```

返回当前启用的数字人配置。游客端根据配置加载对应形象、声音和默认表情。

### 5.7 验收标准

| 验收项 | 通过标准 |
|---|---|
| 多形象选择 | 至少可在 2 到 3 个形象之间选择 |
| 当前形象生效 | 后台切换后，游客端能显示对应形象 |
| 声音配置 | 不同形象可绑定不同声音 |
| 兜底策略 | 如果某个形象加载失败，自动回退默认形象 |
| 景区特色 | 至少有一个形象在颜色、服装或名称上贴近景区文化 |

## 六、地图功能调整

地图功能从第五周首要任务调整为次要增强功能。

只有在数字人、问答和语音问题修复完成后，再接入地图。

### 6.1 游客端地图

游客端只保留必要功能：

- 景点地图
- 点击景点弹窗
- 景点介绍
- 人流量信息

不做评价接口。

### 6.2 后台端地图

后台端只保留运营监控能力：

- 景点地图
- 人流量监控
- 异常点高亮
- 异常点管理入口

不做评价管理。

### 6.3 地图接口建议

地图接口尽量保持简单：

```text
GET /api/map/spots
```

返回所有景点点位、名称、简介、人流等级、等待时间、异常状态。

```text
GET /api/map/spots/{spotId}
```

返回单个景点详情、介绍、人流量、等待时间、是否异常、建议操作。

### 6.4 地图验收标准

如果地图进入实现阶段，验收标准为：

- 游客端能看到景点点位。
- 游客点击景点后能看到介绍和人流量。
- 后台端能看到所有景点的人流状态。
- 异常或拥挤点能高亮。
- 地图失败不影响问答、数字人、语音和主演示流程。

## 七、成员分工建议

### 成员 A：测试、验收和演示脚本

- 整理第五周问题清单，按 P0/P1/P2 分级。
- 补充问答换问法测试集。
- 重点验证问答准确率和高风险问题兜底。
- 整理高频回答清单，标注哪些必须预录语音。
- 编写数字人验收用例：重影、口型、停止播报、重复提问、页面切换。
- 编写语音延迟验收用例，检查语音问答是否控制在 5 秒以内。
- 更新最终演示脚本，把数字人、问答和语音修复作为主线。
- 地图验收与演示素材由 A/B 协作完成。

### 成员 B：后端、RAG、TTS 和接口

- 优化问答检索和 FAQ 兜底。
- 增加同义问法、别名、关键词扩展和规则兜底。
- 对高风险问题提供确定性回答。
- 保证 TTS 或语音播报接口稳定，不阻塞文字回答。
- 整理高频回答预录语音，返回可播放的 `audioUrl`。
- 对非高频回答实现语音生成缓存和超时兜底。
- 为前端提供数字人状态字段，例如 `speaking`、`thinking`、`warning`。
- 提供数字人当前配置接口，支持形象和声音选择。
- 地图接口和默认地图数据由 A/B 协作完成。

### 成员 C：前端、数字人和地图页面

- 优先修复数字人两重显示问题。
- 优先处理口型不同步问题。
- 如果口型无法精准同步，采用数字人固定或轻微动作兜底。
- 保证语音结束后数字人停止动嘴。
- 优化问答页面等待状态、字幕展示和播报控制。
- 接入预录语音和语音生成状态，避免用户长时间等待。
- 增加数字人形象选择，或读取后台形象配置。
- 数字人、问答和语音稳定后，不再主责地图开发，地图由 A/B 协作推进。

## 八、第五周每日安排

| 时间 | 重点任务 | 检查点 |
|---|---|---|
| Day 1 | 定位数字人重影原因；整理问答换问法测试集 | 明确重影原因，完成测试集初版 |

## 九、最终验收标准

第五周最终验收以核心功能稳定为主：

| 验收项 | 通过标准 |
|---|---|
| 问答准确性 | 高频问题和换问法问题能稳定回答，准确率达到 90% 以上 |
| 高风险问题 | 票价、开放时间、路线、安全、拥挤避让等问题有明确兜底 |
| 数字人重影 | 页面中不再出现两重数字人 |
| 数字人口型 | 不出现明显错误口型；无法同步时采用固定或轻微动作兜底 |
| 播报状态 | 语音结束或停止后，数字人不再继续动嘴 |
| 语音回答 | 高频回答可播放预录语音，普通回答有语音生成或明确兜底 |
| 语音延迟 | 语音问答延迟尽量控制在 5 秒以内 |
| 形象管理 | 至少支持多个数字人形象选择，声音可与形象绑定 |
| 主演示流程 | 连续完整演示不崩溃，不依赖地图也能讲清系统价值 |
| 地图功能 | 如完成，则作为加分项展示；由 A/B 完成，不影响核心验收 |

## 十、风险和兜底

1. 如果口型同步无法稳定完成，使用固定数字人或轻微动作，不强行展示错误口型。
2. 如果数字人重影短时间无法彻底定位，先隐藏重复层，保证演示画面干净。
3. 如果问答仍存在不确定性，高风险问题必须使用 FAQ 或规则兜底。
4. 如果实时语音生成不稳定，优先播放高频预录语音。
5. 如果语音生成超过 5 秒，先展示文字回答，并提示语音稍后播放或不可用。
6. 如果数字人不能真实变装，使用多个预设形象切换作为替代方案。
7. 如果地图来不及完成，地图功能暂缓，不影响第五周核心验收。
8. 最终演示优先展示稳定链路，不把不稳定功能放在主线流程中。
