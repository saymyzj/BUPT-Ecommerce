# 秒杀订单测试与演示方案

## 1. 文档目标

本文档用于指导成员 B 准备 Apifox 联调、Java 并发验证、演示视频素材和验收说明。

重点验证：

1. 秒杀不超卖。
2. Redis 原子扣减生效。
3. RabbitMQ 异步削峰生效。
4. 订单消费幂等。
5. MySQL 最终订单数量正确。

## 2. 演示环境

本地服务端口遵守 `docs/部署与启动指南.md`：

| 组件 | 端口 |
| --- | ---: |
| Gateway | 8080 |
| user-service | 8081 |
| product-seckill-service | 8082 |
| order-service | 8083 |
| Redis | 6379 |
| RabbitMQ | 5672 / 15672 |
| MySQL | 3306 |

所有客户端请求通过 Gateway：

```text
http://localhost:8080
```

## 3. 演示前恢复步骤

```text
1. 启动 MySQL、Redis、RabbitMQ。
2. 执行 schema.sql。
3. 执行订单和 MQ 日志清理 SQL。
4. 执行 demo-data.sql。
5. 清理 Redis 中旧 seckill:* key。
6. 清空 RabbitMQ 中旧消息。
7. 启动 gateway-service、user-service、product-seckill-service、order-service。
8. 创建或加载秒杀活动，确认 Redis 库存预热为 100。
```

## 4. Apifox 演示链路

1. `POST /api/auth/admin/login`

观察点：

```text

活动创建成功
Redis 中 seckill:stock:{activityId}=100
```

### 4.2 普通用户链路

1. `POST /api/auth/login`

{
  "code": 0,

  }

## 5. Java 并发测试脚本设计

### 5.1 目标

模拟 10000 个用户同时抢 100 件商品。

验收指标：

```text
成功进入队列数 <= 100
最终订单数 <= 100
Redis 库存 >= 0
同一 userId + activityId 不重复
```

### 5.2 输入参数

Java 脚本建议支持：

```text
baseUrl=http://localhost:8080
activityId=1
totalRequests=10000
concurrency=200
quantity=1
tokenMode=mock-or-login
```

说明：

1. `totalRequests` 表示总请求数。
2. `concurrency` 表示同时并发的线程数。
3. 可用不同用户 ID 模拟不同用户。
4. 如 Gateway 尚未完全实现真实 JWT，可在联调阶段使用固定测试 token。

### 5.3 输出结果

脚本输出：

```text
总请求数
成功 queued 数
库存不足数
重复抢购数
其他失败数
平均响应时间
最大响应时间
```

### 5.4 验证 SQL

```sql
SELECT COUNT(*) FROM orders WHERE activity_id = 1;

SELECT user_id, activity_id, COUNT(*) AS cnt
FROM orders
GROUP BY user_id, activity_id
HAVING cnt > 1;
```

预期：

```text
订单数不超过 100
重复订单查询为空
```

## 6. Redis 观察点

演示时观察：

```text
GET seckill:stock:1
GET seckill:activity:1
GET seckill:result:1:10001
EXISTS seckill:user:1:10001
```

预期：

1. 秒杀前库存为 100。
2. 秒杀后库存减少但不为负。
3. 成功用户存在参与标记。
4. 成功用户结果从 `QUEUEING` 变为 `CREATED`。

## 7. RabbitMQ 观察点

RabbitMQ 管理台：

```text
http://localhost:15672
```

观察：

1. `seckill.order.exchange` 是否存在。
2. `seckill.order.create.queue` 是否有消息进入。
3. 消息是否被 `order-service` 消费。
4. `seckill.order.create.dlq` 是否有失败消息。

演示说明：

```text
秒杀接口返回 queued 后，订单不是立刻同步创建，而是通过 RabbitMQ 排队，由订单服务异步消费。
```

## 8. MySQL 观察点

### 8.1 订单表

```sql
SELECT id, order_no, user_id, activity_id, status, total_amount, created_at
FROM orders
ORDER BY id DESC
LIMIT 10;
```

观察：

```text
status=CREATED
total_amount=seckillPrice * quantity
```

### 8.2 订单明细

```sql
SELECT *
FROM order_items
ORDER BY id DESC
LIMIT 10;
```

### 8.3 MQ 日志

```sql
SELECT message_id, event_type, business_key, status, retry_count
FROM mq_message_logs
ORDER BY id DESC
LIMIT 10;
```

## 9. 失败场景测试

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 库存不足 | 库存抢完后继续请求 | 返回 `10001` |
| 重复抢购 | 同一用户重复抢同一活动 | 返回 `10004` |
| 活动未开始 | 活动开始前请求 | 返回 `10002` |
| 活动已结束 | 活动结束后请求 | 返回 `10003` |
| MQ 投递失败 | 停止 RabbitMQ 后请求 | 返回 `20001`，Redis 回滚 |
| 重复消费 | 重复发送同一消息 | 不重复创建订单 |

## 10. 演示视频建议话术

成员 B 负责讲清楚：

```text
这里不是直接扣数据库库存，而是先把 100 件库存预热到 Redis。
用户秒杀时通过 Lua 脚本一次性检查库存、扣库存、标记用户，保证不超卖。
扣减成功后接口立即返回 queued，不等待订单落库。
订单创建请求进入 RabbitMQ，订单服务异步消费并写入 MySQL。
消费端通过 messageId、orderNo、userId+activityId 保证幂等。
最后我们查询数据库，确认订单数没有超过库存。
```
