# 异常恢复与生产化增强演示说明

## 1. 演示结论

本轮增强没有修改原秒杀、订单、SSE 接口的路径、请求体或统一响应结构。成员 A 已准备的 Apifox 正常链路和默认 `docker-compose.yml` 可以继续使用。新增能力通过管理员接口、独立 HA Compose 和默认关闭的候补开关提供。

建议现场先演示原主链路，再从下列增强场景中选两到三个。不要为了展示全部故障而占用正常业务演示时间。

## 2. 推荐现场顺序

1. 使用原 Apifox 集合完成登录、创建活动、秒杀、结果查询和订单查询。
2. 展示 100 件库存、10000 用户压测结果，说明没有超卖和重复订单。
3. 删除某活动 Redis Key，调用库存重建接口，说明 MySQL 是恢复依据。
4. 投递一条非法 MQ 消息，展示死信记录和管理员重放入口。
5. 时间允许时再展示 Redis 主节点停止后 Sentinel 自动切换。

现场答辩的核心表述：

> 正常链路保持原协议；Redis Lua 负责入口原子扣减，RabbitMQ 负责异步削峰，MySQL 资格记录和订单是最终事实。消息不确定时不贸然返库存，永久失败时先确认无订单，再通过幂等 Lua 最多返还一次库存。后台任务使用数据库租约避免多实例重复补偿。

## 3. 默认环境与兼容性

默认环境仍按原指南启动：

```bash
docker compose up -d
```

各服务仍使用原端口：

| 服务 | 端口 |
|---|---:|
| Gateway | 8080 |
| user-service | 8081 |
| product-seckill-service | 8082 |
| order-service | 8083 |
| ai-service | 8084 |
| push-service | 8085 |

默认 `SECKILL_WAITLIST_ENABLED=false`。库存耗尽时仍返回原“库存不足”，不会改变成员 A 的录屏和 Apifox 断言。新增管理员接口如下：

```text
POST /api/seckill/activities/{activityId}/reconcile
GET  /api/seckill/admin/publish-events
POST /api/seckill/admin/publish-events/{id}/retry
GET  /api/orders/admin/dead-letters
POST /api/orders/admin/dead-letters/{id}/replay
```

## 4. 场景一：10000 用户并发压测

确保默认环境和全部服务已经启动，然后执行：

```bash
MYSQL_CONTAINER=bupt-ecommerce-mysql \
REDIS_CONTAINER=bupt-ecommerce-redis \
node scripts/seckill-load-test.js
```

若本机容器名或端口不同，只需通过环境变量覆盖。脚本会自动创建商品、100 件库存和活动，并发起 10000 个不同用户请求。

通过标准：

- `ordersInMySQL=100`
- `redisStock=0`
- `duplicateOrders=0`
- `activeReservations=0`
- `createdReservations=100`
- `pendingPublishEvents=0`
- `verificationStatus=PASS`

老师问“为什么不是 10000 个请求都进入 MQ”时：

> Redis Lua 在入口只放行有库存的请求，100 个请求进入 RabbitMQ 等待异步落库，其余请求立即得到库存不足。削峰不是把所有无效请求都塞进队列，而是保护后端只处理有效资格。

## 5. 场景二：Redis 数据丢失后重建

先从压测输出记录 `activityId`，删除该活动的 Redis 库存和参与标记：

```bash
docker exec bupt-ecommerce-redis redis-cli DEL \
  seckill:stock:{activityId} \
  seckill:activity:{activityId}
```

用管理员 JWT 调用：

```bash
curl -X POST "http://localhost:8080/api/seckill/activities/{activityId}/reconcile" \
  -H "Authorization: Bearer ${ADMIN_TOKEN}"
```

预期响应包含 `initialStock`、`createdOrders`、`activeReservations` 和 `redisStock`。重建公式为：

```text
Redis 剩余库存 = 初始库存 - 已创建订单 - 有效预留资格
```

这说明 Redis 是高性能运行态，不是唯一事实源；恢复时依据 MySQL 订单和资格记录重建，避免凭空加库存。

## 6. 场景三：死信记录与重放

向原订单交换机投递一条无法解析的消息：

```bash
docker exec bupt-ecommerce-rabbitmq rabbitmqadmin publish \
  exchange=seckill.order.exchange \
  routing_key=seckill.order.create \
  payload='not-json-for-dlq-demo'
```

消费者会显式拒绝消息，RabbitMQ 根据原队列的 DLX 配置将其路由到死信队列；死信消费者持久化后确认消息。随后用管理员 JWT 查询：

```bash
curl "http://localhost:8080/api/orders/admin/dead-letters?page=1&pageSize=20" \
  -H "Authorization: Bearer ${ADMIN_TOKEN}"
```

可看到 `RECEIVED`、原始 payload、失败头信息和重放次数。重放入口为：

```bash
curl -X POST "http://localhost:8080/api/orders/admin/dead-letters/{id}/replay" \
  -H "Authorization: Bearer ${ADMIN_TOKEN}"
```

非法 JSON 重放后仍会再次成为死信，这是正确结果；真实运维中应先修正数据或代码，再重放。重放沿用原 `messageId`，即使消息重复到达，订单唯一索引和消费幂等日志也不会生成重复订单。

## 7. 场景四：RabbitMQ 暂时不可用

停止 RabbitMQ：

```bash
ACTION=stop COMPONENT=rabbitmq node scripts/seckill-fault-control.js
```

此时发起一次有效秒杀。资格和待投递事件已经先写入 MySQL，接口不会因为 Confirm 不确定而直接返还 Redis 库存。查询管理员投递事件可看到 `UNKNOWN` 或 `PENDING`：

```bash
curl "http://localhost:8080/api/seckill/admin/publish-events?page=1&pageSize=20" \
  -H "Authorization: Bearer ${ADMIN_TOKEN}"
```

恢复 RabbitMQ：

```bash
ACTION=start COMPONENT=rabbitmq node scripts/seckill-fault-control.js
```

后台任务会使用同一 `messageId` 重试，最终事件变为 `SENT` 并创建订单。达到自动重试上限的 `DEAD` 事件可调用管理员重试接口恢复。

## 8. 场景五：Redis Sentinel 自动切换

该场景使用独立环境，不替换默认 Compose：

```bash
docker compose stop redis
docker compose -f docker-compose-ha.yml up -d
```

HAProxy 在宿主机 `6380` 提供稳定 Redis 主节点入口；Sentinel 负责选主，两个副本复制数据。启动服务时启用 `ha` Profile，或保持 `REDIS_HOST=localhost REDIS_PORT=6380`。

停止当前主节点：

```bash
ACTION=stop COMPONENT=redis-primary node scripts/seckill-fault-control.js
```

约 5 至 10 秒后检查：

```bash
docker exec bupt-ecommerce-redis-sentinel-1 \
  redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster

docker exec bupt-ecommerce-redis-replica-2 redis-cli -h redis-proxy -p 6379 PING
```

预期 Sentinel 返回新的主节点，HAProxy 返回 `PONG`，应用无需重启即可继续访问。最后恢复原节点：

```bash
ACTION=start COMPONENT=redis-primary node scripts/seckill-fault-control.js
```

原主节点会作为副本重新加入。课程项目实现的是可复现的 Sentinel 主从切换；跨机房 Redis Cluster、持久化备份和监控告警仍属于后续生产部署范围。

## 9. 场景六：公平候补

公平候补默认关闭，只在单独启动秒杀服务时开启：

```bash
SECKILL_WAITLIST_ENABLED=true \
SECKILL_WAITLIST_MAX_SIZE=200 \
./mvnw -pl product-seckill-service spring-boot:run
```

库存耗尽后的请求仍沿用原 `queued/QUEUEING` 响应，不新增客户端字段。候补顺序使用 MySQL 自增序号，由服务端生成，不相信客户端时间。若已获得资格的用户因服务端永久失败且确认没有订单，系统幂等释放一个库存，后台任务按序提升最早候补者。

用户自身参数错误等不可重试问题不会插队；网络超时属于“不确定”，系统先按原 `requestId/messageId` 查询和重试，不能直接认定失败并返库存。

## 10. 永久失败与补偿任务说明

订单落库失败后，资格进入 `RETRYING`，补偿任务按指数退避重试，默认最多 6 次。每次执行前都先检查是否已经存在订单：

1. 已有订单：资格修正为 `CREATED`，绝不返库存。
2. 暂时性失败：保留原资格，更新下次重试时间。
3. 达到上限且确认无订单：进入 `RELEASE_PENDING`。
4. 执行 Redis 幂等释放 Lua：只有补偿标记不存在时才库存加一。
5. 释放成功：资格变为 `RELEASED`，结果变为 `FAILED`，公平模式可提升候补队首。

补偿扫描和可靠投递扫描都通过 MySQL `task_leases` 抢占任务。即使部署多个实例，同一时刻也只有租约持有者执行，业务幂等约束仍作为第二道保护。

## 11. 现场恢复与回滚

若增强场景影响演示，立即恢复默认环境：

```bash
docker compose -f docker-compose-ha.yml down
docker compose up -d
```

并确认候补开关未设置或为：

```bash
SECKILL_WAITLIST_ENABLED=false
```

原 Apifox 集合只依赖 Gateway `http://localhost:8080`，不调用新增管理接口，因此恢复默认中间件后即可继续原演示。
