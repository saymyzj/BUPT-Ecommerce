# 附加地图功能规划

> 定位：地图功能作为第五周的附加增强项，不作为核心验收前置条件。只有在数字人重影、口型表现和问答准确性修复完成后，再进入地图开发。若时间不足，地图可降级为静态景区示意图或暂缓。地图由 A/B 负责，C 不作为主责。

## 一、功能目标

地图功能的目标是增强景区导览体验和后台运营感：

1. 游客端帮助游客了解景点位置、介绍和当前人流量。
2. 后台端帮助管理员查看景区整体人流状态和异常点。
3. 地图数据复用已有景点和人流状态，不另起一套数据口径。
4. 不实现评价接口，不做复杂地图 SDK 强依赖。

## 二、功能边界

### 2.1 本期实现

游客端：

- 景点地图
- 点击景点弹窗
- 景点介绍
- 人流量信息
- 等待时间或拥挤状态

后台端：

- 景点地图
- 人流量监控
- 异常点高亮
- 异常点管理入口

### 2.2 本期不实现

- 游客评价接口
- 评价列表管理
- 真实 GPS 定位
- 复杂导航算法
- 真实地图 SDK 深度接入
- 实时轨迹追踪
- 多楼层/室内地图

## 三、游客端地图规划

### 3.1 页面入口

游客端新增“景区地图”入口，可放在：

- 首页功能入口
- 导览页面
- 路线推荐页面旁边

入口名称建议：

```text
景区地图
```

### 3.2 地图展示内容

游客端地图展示：

- 景区平面示意图
- 景点点位
- 景点名称
- 人流状态颜色
- 拥挤景点提示

人流状态颜色建议：

| 状态 | 颜色 | 含义 |
|---|---|---|
| LOW | 绿色 | 人少，适合前往 |
| MEDIUM | 黄色 | 人流正常 |
| HIGH | 橙色 | 人较多，需要注意 |
| CROWDED | 红色 | 拥挤，建议避让 |

### 3.3 点击景点弹窗

游客点击景点后弹出详情卡片。

弹窗字段建议：

| 字段 | 说明 |
|---|---|
| 景点名称 | spotName |
| 景点介绍 | introduction |
| 当前人流量 | currentVisitors |
| 人流状态 | crowdLevel |
| 预计等待时间 | waitMinutes |
| 建议停留时间 | recommendedStayMinutes |
| 是否建议前往 | recommendVisit |
| 替代景点 | alternativeSpotName |

游客端详情重点是“能不能去、为什么、去哪替代”。

### 3.4 游客端交互规则

1. 点击普通景点，展示景点介绍和当前人流。
2. 点击拥挤景点，优先提示“当前人流较多，建议错峰或前往替代景点”。
3. 点击异常景点，提示异常原因，不建议前往。
4. 如果地图接口失败，页面显示“地图数据加载失败”，不影响问答和数字人。
5. 如果人流数据缺失，显示“暂无人流数据”，不使用假数据冒充实时状态。

## 四、后台端地图规划

### 4.1 页面入口

后台端新增“景区地图”或“地图监控”页面。

入口位置建议：

- 后台侧边栏
- 景点管理模块下
- 运营监控模块下

入口名称建议：

```text
地图监控
```

### 4.2 后台地图展示内容

后台地图展示：

- 全部景点点位
- 人流状态颜色
- 拥挤点高亮
- 异常点标识
- 更新时间

后台端重点是运营监控，不是游客导览。

### 4.3 点击景点运营卡片

后台点击景点后展示运营信息。

字段建议：

| 字段 | 说明 |
|---|---|
| 景点名称 | spotName |
| 当前人流量 | currentVisitors |
| 最大承载量 | capacity |
| 拥挤指数 | crowdIndex |
| 人流状态 | crowdLevel |
| 预计等待时间 | waitMinutes |
| 异常状态 | abnormal |
| 异常原因 | abnormalReason |
| 替代景点 | alternativeSpotName |
| 更新时间 | updatedAt |

### 4.4 后台管理动作

后台端可以提供轻量管理入口：

- 跳转到景点管理
- 跳转到模拟控制台
- 查看异常点
- 手动刷新人流状态

本期不强制在地图上直接编辑景点数据，避免范围扩大。

## 六、数据设计建议

如果当前已有景点和人流数据，应优先复用已有表和字段。

地图新增字段建议：

| 字段 | 说明 |
|---|---|
| spot_id | 景点 ID |
| spot_name | 景点名称 |
| map_x | 地图相对 X 坐标 |
| map_y | 地图相对 Y 坐标 |
| introduction | 景点介绍 |
| capacity | 最大承载量 |
| current_visitors | 当前人流量 |
| crowd_level | 人流等级 |
| crowd_index | 拥挤指数 |
| wait_minutes | 预计等待时间 |
| abnormal | 是否异常 |
| abnormal_reason | 异常原因 |
| alternative_spot_id | 替代景点 ID |
| updated_at | 更新时间 |

如果时间不足，可以不改数据库，先使用默认地图配置文件或初始化数据。

## 七、前端实现建议

### 7.1 地图形式

优先采用景区平面示意图或相对坐标地图。

推荐方案：

- 使用一张景区背景图。
- 用绝对定位渲染景点点位。
- 点位颜色表示人流状态。
- 点击点位展示弹窗。

暂不建议一开始接入真实地图 SDK，因为 SDK 权限、网络、定位和样式适配风险较高。

### 7.2 点位渲染规则

点位样式：

- 普通点：圆点 + 景点名称
- 拥挤点：红色圆点 + 闪烁或高亮
- 异常点：红色/紫色标识 + 警告图标
- 推荐替代点：绿色高亮

### 7.3 失败兜底

地图接口失败时：

- 显示错误提示
- 保留页面基本结构
- 不影响游客问答、数字人和其他功能

## 八、开发顺序

建议开发顺序：

1. A 整理景点点位和地图展示规则。
2. B 提供 `GET /api/map/spots` 和 `GET /api/map/spots/{spotId}`。
3. A/B 完成后台地图基础页面。
4. A/B 完成游客端地图基础页面。
5. A/B 联调人流状态和异常点高亮。
6. A 编写地图验收用例和演示脚本。

## 九、验收标准

| 验收项 | 通过标准 |
|---|---|
| 游客端地图 | 能看到景点点位，点击后显示介绍和人流量 |
| 后台端地图 | 能看到所有景点人流状态 |
| 人流状态 | LOW/MEDIUM/HIGH/CROWDED 能用颜色区分 |
| 异常点 | 后台端异常点能高亮显示 |
| 数据一致性 | 游客端、后台端和景点管理使用同一套人流数据 |
| 失败兜底 | 地图失败不影响问答、数字人和主演示流程 |

## 十、风险与降级

1. 如果真实地图 SDK 不稳定，使用景区平面示意图。
2. 如果后端接口来不及完成，使用静态默认地图数据演示，但必须明确标注为演示数据。
3. 如果游客端和后台端都来不及完成，优先完成后台端地图监控。
4. 如果核心数字人和问答仍未稳定，地图功能暂缓。
5. 地图不得影响最终主演示链路。
