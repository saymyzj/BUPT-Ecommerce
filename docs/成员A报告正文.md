# 摘要

随着 Web 后端系统从单体应用逐渐演进为面向高并发、高可用和智能化服务的分布式架构，传统以数据库为中心的同步处理方式已难以满足秒杀、实时通知和 AI 咨询等复杂业务场景的要求。本项目选择课程题目一“AI 驱动的高并发秒杀与智能电商后台系统”，设计并实现了一个面向本地验收的微服务原型系统。系统以 API Gateway 作为统一入口，结合 JWT 完成身份认证与角色权限控制，通过 MySQL 保存用户、商品、订单等最终业务数据，通过 Redis 承担秒杀库存预热、原子扣减和结果缓存，通过 RabbitMQ 实现订单创建的异步削峰，通过 SSE 实现订单创建结果实时推送，并通过 AI 服务接入大语言模型能力，为用户提供商品咨询与购买建议。

本报告围绕系统需求分析、总体架构设计、接口契约、数据库设计、高并发秒杀链路、异步订单削峰、实时推送、AI 智能导购、测试验收以及生产环境演进方案展开。报告重点说明本地原型如何验证“统一入口、高并发防超卖、异步削峰、实时反馈和 AI 集成”等核心能力，并进一步分析在百万日活等生产场景下，系统如何通过 Gateway 集群、微服务多实例部署、Redis 高可用、RabbitMQ 集群、MySQL 主从复制、限流熔断、日志监控和链路追踪等方案提升整体可用性、扩展性和可维护性。

# 1 绪论

## 1.1 项目背景

在现代 Web 后端系统中，电商平台通常需要同时面对用户认证、商品管理、库存管理、订单创建、实时通知和智能咨询等多类业务需求。其中，秒杀业务具有请求瞬时集中、库存数量有限、用户竞争激烈和订单写入压力突增等特点，是检验后端系统高并发处理能力的重要场景。如果系统仍采用普通下单方式，即用户请求直接访问数据库并同步扣减库存，则在高并发条件下容易出现数据库行锁竞争严重、接口响应时间上升、订单重复创建甚至库存超卖等问题。

与此同时，随着大语言模型服务逐渐进入业务系统，传统电商后台也开始从单纯的数据查询系统演进为具备智能导购能力的交互式系统。用户不仅希望查看商品详情，还希望围绕商品特点、价格、适用场景等问题获得自然语言形式的购买建议。然而，第三方大语言模型 API 通常存在响应时间较长、调用成本较高、并发额度有限和外部依赖不稳定等问题，因此 AI 调用链路也需要配套缓存、限流、超时和降级机制，不能简单地同步直连模型服务。

基于上述背景，本项目以“AI 驱动的高并发秒杀与智能电商后台系统”为主题，构建一个以微服务为基础的本地原型系统。项目通过 Gateway、Redis、RabbitMQ、MySQL、SSE 和 LLM API 等技术组合，模拟真实电商后台中的高并发秒杀、异步订单创建、实时订单结果推送和 AI 商品咨询等关键链路，重点体现现代后端系统在高并发、高可用和智能化方向上的架构设计思路。

## 1.2 选题说明

本项目选择课程指导书中的题目一，即 AI 驱动的“高并发秒杀与智能电商”后台系统。该题目既包含用户注册登录、商品管理、库存管理、订单查询等基础支撑功能，也包含统一入口控制、高并发防超卖、异步订单削峰、实时结果推送和 AI 智能导购等核心架构功能，能够较全面地覆盖本课程对现代 Web 后端开发技术的考查要求。

从课程目标来看，本项目的重点并不在于实现完整电商平台的所有业务闭环，而在于通过一个聚焦的电商秒杀场景说明后端系统如何处理高并发请求、如何利用缓存和消息队列降低数据库压力、如何通过统一网关收敛认证与权限逻辑、如何通过实时通信提升用户反馈体验，以及如何在业务系统中合理接入大语言模型能力。

因此，本项目将业务范围限定在“可演示、可解释、可验收”的核心主链路内。系统不实现完整支付闭环、复杂营销体系和多端商城前端，而是重点实现管理员创建商品和秒杀活动、普通用户登录并参与秒杀、Redis 原子扣减库存、RabbitMQ 异步创建订单、MySQL 保存最终订单、SSE 推送订单结果、AI 服务提供商品咨询等功能。

## 1.3 项目目标

本项目的总体目标是设计并实现一个面向课程验收的高并发秒杀与智能电商后台原型系统，在本地环境中验证微服务拆分、统一网关入口、缓存防超卖、消息队列削峰、实时推送和 AI 咨询等关键能力。

在功能层面，系统需要支持用户注册、登录、角色识别和 JWT 鉴权；支持管理员创建商品、设置库存和创建秒杀活动；支持普通用户查询商品、参与秒杀、查询秒杀结果和查看订单；支持订单创建成功后向用户实时推送结果；支持用户围绕商品信息发起 AI 咨询，并在大语言模型不可用时返回明确的降级结果。

在架构层面，系统需要体现微服务拆分思想。所有客户端请求统一经过 Gateway，由 Gateway 负责路由转发、JWT 校验、角色权限判断和基础请求治理。业务服务按照职责拆分为用户服务、商品秒杀服务、订单服务、推送服务和 AI 服务。系统通过 MySQL 保存最终业务事实，通过 Redis 处理秒杀过程中的高频状态，通过 RabbitMQ 将订单创建请求异步化，从而避免数据库直接承受秒杀请求洪峰。

在报告层面，项目需要在本地原型之外进一步说明正式生产环境演进方案，包括 Gateway 多实例和负载均衡、微服务水平扩容、Redis Sentinel 或 Cluster、RabbitMQ 集群、MySQL 主从复制和读写分离、热点库存治理、消息可靠性补偿、AI 调用缓存限流和日志监控告警等内容，以证明系统具备从课程原型向生产级架构演进的设计基础。

## 1.4 系统核心业务流程概述

系统核心业务流程围绕“管理员准备秒杀活动”和“普通用户参与秒杀并获得结果”两条线展开。管理员首先通过认证接口登录系统，获得具备 ADMIN 角色的 JWT Token；随后通过 Gateway 调用商品管理接口创建商品、设置库存，并创建对应的秒杀活动。秒杀活动创建后，商品秒杀服务将活动信息和活动库存预热到 Redis，为后续高并发秒杀请求做准备。

普通用户通过注册或登录接口获得 CUSTOMER 角色的 JWT Token。在参与秒杀前，用户可通过推送接口建立 SSE 连接，用于接收订单创建结果。用户发起秒杀请求时，请求首先进入 Gateway，Gateway 校验 Token 和角色权限后转发至商品秒杀服务。商品秒杀服务不直接修改数据库库存，而是执行 Redis Lua 脚本，在 Redis 内一次性完成活动校验、重复参与校验、库存判断、库存扣减、用户参与标记和秒杀结果写入。扣减成功后，商品秒杀服务向 RabbitMQ 投递订单创建消息，并立即向用户返回 QUEUEING 状态。

订单服务异步消费 RabbitMQ 中的订单创建消息，完成消息幂等检查、订单主表写入、订单明细写入和消息日志更新。订单真正落库成功后，订单服务更新 Redis 中的秒杀结果，并通过推送服务向当前用户发送订单创建成功事件。用户也可以通过秒杀结果查询接口或订单查询接口主动获取最终状态。

在商品咨询场景中，用户通过 Gateway 调用 AI 咨询接口。AI 服务根据商品详情、秒杀活动信息和用户问题构造上下文，优先检查缓存，未命中时调用大语言模型 API 生成回答。如果 LLM 未配置、调用超时或外部服务失败，则系统明确返回 AI 服务暂不可用的业务码和降级回答，避免将失败伪装为正常 AI 响应。

## 2.2 用户与权限需求

用户与权限模块需要为整个系统提供统一的身份识别和访问控制能力。系统用户分为普通用户和管理员两类角色，其中普通用户对应 CUSTOMER，主要权限包括浏览商品、参与秒杀、查询个人订单、建立推送连接和使用 AI 咨询；管理员对应 ADMIN，主要权限包括创建商品、设置库存、创建秒杀活动和查询管理侧订单数据。

系统需要提供用户注册、用户登录、管理员登录、当前用户信息查询和注销等接口。用户登录成功后，系统签发 JWT Token，并在 Token 载荷中包含 userId、username、role、iat 和 exp 等字段。客户端访问需要登录的接口时，应在 HTTP 请求头中携带统一的鉴权头：

```text
Authorization: Bearer <token>
```

Gateway 负责对客户端请求进行统一鉴权。对于 PUBLIC 接口，Gateway 允许未登录用户访问；对于 CUSTOMER 接口，Gateway 需要确认用户已登录且具备普通用户或管理员身份；对于 ADMIN 接口，Gateway 必须确认用户具备管理员角色。若请求未携带 Token、Token 无效或 Token 已过期，系统返回 401；若用户已登录但角色权限不足，系统返回 403。

为避免各业务服务重复实现认证逻辑，本项目将认证和权限判断尽可能收敛到 Gateway。业务服务默认只信任 Gateway 注入的用户上下文信息，不自行解析客户端侧 Token，也不接受缺少用户上下文的直连内部服务请求。该设计可以保证认证规则的一致性，并降低商品、秒杀、订单、推送和 AI 服务中的重复鉴权代码。

## 2.7 非功能性需求分析

除基础业务功能外，本项目还需要满足高并发、高可用、可维护、安全性和可观测性等非功能性需求。

在高并发方面，系统需要能够解释并验证 100 件库存面对大量并发请求时不发生超卖。秒杀接口不能直接扣减数据库库存，而应通过 Redis 库存预热和 Lua 原子扣减降低数据库压力，并通过 MQ 将订单创建异步化。订单服务需要通过幂等设计防止重复消息导致重复订单。

在高可用方面，本地原型虽然采用单机部署，但报告中需要说明生产环境下如何消除单点故障。Gateway、业务微服务、Redis、RabbitMQ 和 MySQL 均需要具备从单实例向集群或主从架构演进的方案，以支撑更高流量和故障恢复需求。

在安全性方面，系统需要统一使用 JWT 进行身份认证，敏感配置如数据库密码、JWT 密钥、RabbitMQ 密码和 LLM API Key 不得提交到代码仓库，而应通过环境变量或本地未提交配置注入。不同角色访问不同接口时必须进行权限校验，普通用户不能访问管理员商品管理和订单管理接口。

在可维护性方面，系统需要通过接口契约、统一响应格式、错误码、数据库文档、Redis Key 文档和 MQ 消息契约降低多人协作成本。所有跨服务交互字段必须文档化，避免不同服务之间出现字段命名不一致或语义漂移。

在可观测性方面，系统需要能够通过日志、测试集合、Redis 状态、RabbitMQ 队列、MySQL 数据和推送结果观察主链路运行情况。生产环境中还应进一步引入指标监控、链路追踪和告警机制，以便及时发现接口错误率升高、MQ 消息积压、Redis 库存异常和 AI 调用失败率升高等问题。

# 3 系统总体架构设计

## 3.1 总体架构设计原则

本项目总体架构遵循统一入口、职责分离、契约优先、异步削峰和最终一致性等设计原则。

首先，系统采用 Gateway 作为所有客户端请求的统一入口。客户端不直接访问 user-service、product-seckill-service、order-service、push-service 或 ai-service，而是统一访问 `http://localhost:8080`，再由 Gateway 根据路径规则转发到对应服务。该原则有助于统一认证、权限、跨域、日志和后续限流策略。

其次，系统按照业务职责进行服务拆分。用户服务负责注册、登录和用户信息；商品秒杀服务负责商品、库存、活动和 Redis 秒杀扣减；订单服务负责 MQ 消费、订单落库和订单查询；推送服务负责订单结果实时推送；AI 服务负责商品咨询和 LLM 调用。各服务之间通过明确的接口、消息或缓存 Key 进行协作，避免业务边界混乱。

第三，系统采用契约优先的协作方式。接口路径、请求字段、响应结构、错误码、Redis Key、MQ 消息体和数据库表结构均先形成文档约束，再进入实现阶段。该方式能够保证多人协作时的接口一致性，也便于最终报告、Apifox 集合和演示视频使用统一口径。

第四，系统将高并发处理与最终业务落库解耦。秒杀请求进入系统后，Redis 负责快速完成资格抢占和库存扣减，RabbitMQ 负责将抢到资格的请求排队，订单服务负责按自身能力异步消费并写入 MySQL。该设计避免数据库直接承受秒杀请求洪峰，也使系统具备更好的可扩展性。

最后，系统采用最终一致性思路处理秒杀订单链路。秒杀接口返回 QUEUEING 时表示用户已进入订单创建队列，而不是订单已经创建完成。订单真正落库后，系统再更新 Redis 秒杀结果并通过 SSE 推送给用户。该设计符合高并发秒杀场景中“快速响应、异步处理、最终确认”的业务特征。

## 3.2 本地原型系统架构图

本地原型系统由客户端、Gateway、多个业务微服务和基础中间件组成。客户端包括 Apifox 和 simple-test-page，所有请求均通过 Gateway 进入后端系统。Gateway 根据接口路径将请求转发至用户服务、商品秒杀服务、订单服务、推送服务或 AI 服务。MySQL、Redis 和 RabbitMQ 作为共享中间件，为不同业务服务提供持久化、缓存和异步消息能力。

在该架构中，MySQL 保存用户、商品、库存、秒杀活动、订单、订单明细和消息日志等最终业务数据；Redis 保存秒杀活动库存、用户参与标记、秒杀结果和 AI 问答缓存等高频访问状态；RabbitMQ 接收商品秒杀服务投递的订单创建消息，并由订单服务异步消费；推送服务通过 SSE 维护客户端连接，用于在订单创建成功后向用户发送实时结果；AI 服务调用商品上下文和大语言模型 API，为用户提供商品咨询能力。

本地原型的重点不是部署规模，而是验证架构链路的正确性。通过该架构可以清晰展示：客户端请求经过统一入口进入系统，秒杀资格在 Redis 中完成快速判断，订单创建通过 RabbitMQ 削峰进入订单服务，最终业务事实写入 MySQL，用户结果通过推送服务或查询接口获得。

## 3.3 服务拆分与职责划分

本项目将后端系统拆分为多个相对独立的服务，每个服务承担明确的业务职责。服务拆分结果如表 3-1 所示。

表 3-1 服务拆分与职责说明

| 服务名称 | 核心职责 |
| --- | --- |
| gateway-service | 统一入口、路由转发、JWT 校验、权限控制、跨域与基础日志 |
| user-service | 用户注册、用户登录、管理员登录、用户信息查询、Token 签发辅助 |
| product-seckill-service | 商品管理、库存设置、秒杀活动创建、Redis 预热、Lua 原子扣减 |
| order-service | RabbitMQ 消费、订单幂等落库、订单查询、消息日志记录 |
| push-service | SSE 连接管理、订单创建结果推送 |
| ai-service | 商品咨询、商品上下文构造、LLM API 调用、缓存与降级 |

该拆分方式与业务主链路保持一致。Gateway 和 user-service 构成系统访问控制基础；product-seckill-service 和 order-service 构成高并发秒杀与订单创建核心；push-service 提供订单结果实时反馈；ai-service 提供智能导购能力。服务职责清晰后，后续接口契约、数据库表归属、Redis Key 归属和 MQ 消息归属也可以相应明确。

## 3.4 Gateway 统一入口设计

Gateway 是系统的统一入口，负责将客户端请求路由到内部业务服务，并承担统一认证、权限判断和基础请求治理职责。客户端统一访问：

```text
http://localhost:8080
```

本项目的 Gateway 路由规划如下：

```text
/api/auth/**       -> user-service
/api/users/**      -> user-service
/api/products/**   -> product-seckill-service
/api/seckill/**    -> product-seckill-service
/api/orders/**     -> order-service
/api/ai/**         -> ai-service
/api/push/**       -> push-service
```

Gateway 只承担通用能力，不承载具体业务逻辑。例如，Gateway 可以判断某接口是否需要 ADMIN 权限，但不应在 Gateway 中实现创建商品、扣减库存或创建订单等业务操作。这样可以保持网关职责收敛，避免网关随着业务复杂度上升而变成新的单体服务。

在认证流程中，Gateway 解析客户端携带的 `Authorization: Bearer <token>` 请求头，校验 Token 签名和有效期，并根据接口权限要求判断用户角色是否合法。认证通过后，Gateway 将用户上下文传递给内部服务，内部服务基于该上下文处理业务。该方式使各业务服务无需重复解析 JWT，有利于统一权限规则并减少重复代码。

对于内部接口，例如 `/api/orders/internal/**`，Gateway 需要进行额外拦截，避免客户端或 Apifox 演示流程直接调用内部服务间接口。内部服务间调用应通过内部 Token 或服务间认证机制识别，防止内部能力暴露为公共入口。

## 3.5 系统核心数据流

系统核心数据流可分为登录认证流、秒杀订单流、推送通知流和 AI 咨询流。

登录认证流中，客户端向 Gateway 发起登录请求，Gateway 转发至 user-service。user-service 校验用户身份后返回 JWT Token。客户端后续访问受保护接口时携带该 Token，Gateway 负责完成认证和角色权限判断。

秒杀订单流中，客户端向 Gateway 发起秒杀请求，Gateway 校验用户身份后转发至 product-seckill-service。商品秒杀服务执行 Redis Lua 脚本完成库存扣减和用户参与标记写入。扣减成功后，商品秒杀服务向 RabbitMQ 投递订单创建消息，并返回 QUEUEING。order-service 异步消费该消息，将订单写入 MySQL，并更新 Redis 中的秒杀结果。

推送通知流中，用户登录后通过 Gateway 访问 push-service 建立 SSE 连接。订单服务创建订单成功后，将订单结果事件发送给推送服务，推送服务根据用户维度找到对应连接，并向当前用户推送 ORDER_CREATED 事件。即使推送失败，订单最终状态仍以 MySQL 为准，用户可以通过查询接口获取结果。

AI 咨询流中，客户端向 Gateway 发起商品咨询请求。Gateway 通过权限校验后转发至 ai-service。AI 服务根据 productId 查询商品上下文，检查缓存是否命中，必要时调用大语言模型 API 生成回答。若 LLM 调用失败或超时，则返回明确的降级业务码和兜底回答。

# 4 接口契约与统一规范设计

## 4.1 RESTful 接口设计规范

本项目采用 RESTful 风格组织 HTTP 接口，以资源路径表达业务对象，以 HTTP 方法表达操作语义。接口统一以 `/api` 为前缀，并通过 Gateway 暴露给客户端。各业务模块按照资源类型划分路径，例如认证与用户接口使用 `/api/auth/**` 和 `/api/users/**`，商品接口使用 `/api/products/**`，秒杀活动接口使用 `/api/seckill/**`，订单接口使用 `/api/orders/**`，AI 咨询接口使用 `/api/ai/**`，推送接口使用 `/api/push/**`。

接口方法设计遵循常见语义：查询资源使用 GET，创建资源使用 POST，更新资源使用 PUT，注销或触发类操作根据语义使用 POST。分页查询接口统一使用 `page`、`pageSize`、`keyword`、`status`、`startTime` 和 `endTime` 等查询参数，便于 Apifox 测试集合和前端测试页面统一处理。

所有新增接口、字段改名、路径调整或权限变化，都应先更新接口契约文档，再修改代码实现。该规则可以减少多人协作中出现的接口不一致问题，也能保证最终报告、Apifox 集合和代码实现保持同一口径。

## 4.2 统一响应格式设计

为避免不同服务返回多套响应结构，本项目规定所有 HTTP 接口统一返回如下格式：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

其中，`code` 表示业务状态码，`0` 表示成功；`message` 表示人类可读的响应说明；`data` 表示业务数据，失败时可以为空。失败响应示例如下：

```json
{
  "code": 400,
  "message": "请求参数错误",
  "data": null
}
```

分页查询接口统一将分页数据放在 `data` 字段中，结构如下：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "records": [],
    "page": 1,
    "pageSize": 10,
    "total": 100
  }
}
```

统一响应格式能够降低前端测试页面、Apifox 脚本和跨服务调用的处理成本。无论请求访问用户、商品、秒杀、订单、推送还是 AI 模块，调用方均可以按照相同结构读取状态码、说明信息和业务数据。

## 4.3 错误码设计

系统错误码分为通用错误码和业务错误码两类。通用错误码覆盖参数错误、未登录、无权限、资源不存在、业务冲突、限流和服务器内部错误等常见场景；业务错误码覆盖秒杀、MQ 和 AI 模块中的特定失败场景。

表 4-1 通用错误码说明

| code | message | 含义 |
| ---: | --- | --- |
| 0 | success | 成功 |
| 400 | 请求参数错误 | 参数缺失、格式错误、校验失败 |
| 401 | 未登录或 Token 无效 | 未携带 Token、Token 过期、Token 非法 |
| 403 | 无权限 | 角色不匹配或接口权限不足 |
| 404 | 资源不存在 | 查询对象不存在 |
| 409 | 业务冲突 | 重复提交、状态冲突 |
| 429 | 请求过于频繁 | 限流触发 |
| 500 | 服务器内部错误 | 未预期异常 |

表 4-2 业务错误码说明

| code | message | 含义 |
| ---: | --- | --- |
| 10001 | 库存不足 | 秒杀库存不足 |
| 10002 | 秒杀活动未开始 | 活动开始前请求 |
| 10003 | 秒杀活动已结束 | 活动结束后请求 |
| 10004 | 用户已参与该活动 | 重复抢购 |

## 4.4 JWT 认证机制设计

JWT 是本项目中客户端身份认证的基础机制。用户或管理员登录成功后，系统签发 JWT Token。客户端后续访问受保护接口时，将 Token 放入请求头：

```text
Authorization: Bearer <token>
```

JWT 载荷建议包含以下字段：

```json
{
  "userId": 10001,
  "username": "alice",
  "role": "CUSTOMER",
  "iat": 1710000000,
  "exp": 1710003600
}
```

其中，`userId` 用于标识用户主键，`username` 用于标识用户名，`role` 用于角色权限判断，`iat` 表示签发时间，`exp` 表示过期时间。系统统一使用 `JWT_SECRET` 完成 Token 签名和校验，真实密钥不得提交至仓库。

Gateway 是 Token 校验的主要执行位置。请求进入 Gateway 后，Gateway 解析 Token、校验签名、检查有效期，并根据路由权限要求判断用户是否具备访问资格。认证通过后，Gateway 将用户上下文传递给内部服务。业务服务默认只信任 Gateway 注入的上下文，直连内部服务且缺少上下文信息的请求视为未登录。

注销功能可以采用客户端删除本地 Token、服务端记录 Token 黑名单或记录用户注销时间等方式实现。本地原型阶段若暂不实现服务端黑名单，也应在文档中说明注销主要清除客户端状态。

## 4.5 角色权限控制设计

系统角色分为 CUSTOMER 和 ADMIN。CUSTOMER 表示普通用户，主要用于浏览商品、发起秒杀、查询个人订单、建立推送连接和使用 AI 咨询。ADMIN 表示管理员，主要用于创建商品、设置库存、创建秒杀活动和查询管理侧订单数据。

接口权限分为 PUBLIC、CUSTOMER 和 ADMIN 三类。PUBLIC 接口无需登录即可访问，例如注册、登录、商品列表、商品详情和秒杀活动详情。CUSTOMER 接口要求用户登录，例如发起秒杀、查询秒杀结果、查询个人订单、AI 咨询和建立推送连接。ADMIN 接口仅管理员可访问，例如创建商品、设置库存、创建秒杀活动和管理员订单查询。

表 4-3 接口权限分级说明

| 权限级别 | 访问要求 | 典型接口 |
| --- | --- | --- |
| PUBLIC | 无需登录 | 注册、登录、商品列表、商品详情、活动详情 |
| CUSTOMER | 登录用户 | 发起秒杀、查询订单、AI 咨询、建立推送连接 |
| ADMIN | 管理员 | 创建商品、设置库存、创建秒杀活动、管理员订单查询 |

权限控制应在 Gateway 层统一执行，业务服务可根据 Gateway 注入的用户上下文进行必要的二次校验。例如，订单详情接口不仅需要用户已登录，还需要确认当前用户只能查看自己的订单；管理员订单接口则必须要求 ADMIN 角色。

# 10 技术选型依据分析

## 10.1 Gateway 技术选型依据

本项目引入 Gateway 的主要原因是系统采用微服务拆分后，需要一个统一入口处理客户端请求。如果客户端直接访问各个业务服务，则认证、权限、跨域、日志、限流和路由规则会分散在多个服务中，导致重复实现和维护困难。尤其在本项目中，用户服务、商品秒杀服务、订单服务、推送服务和 AI 服务均需要识别用户身份，如果每个服务都独立解析 Token 和判断权限，不仅会增加代码重复，也容易造成权限策略不一致。

Gateway 可以将通用入口能力集中处理。客户端统一访问 `http://localhost:8080`，Gateway 根据路径规则将请求转发到对应服务。对于需要登录的接口，Gateway 统一解析 JWT，校验签名和有效期，并根据接口权限要求判断用户角色。认证通过后，Gateway 将用户上下文传递给内部服务，内部服务基于该上下文处理业务逻辑。

在秒杀场景中，Gateway 还可以作为生产环境限流和流量治理的第一道防线。秒杀活动开始时，大量请求会同时进入系统，Gateway 层可以根据 IP、用户、接口路径或活动 ID 进行限流，提前拦截异常流量，避免无效请求直接冲击秒杀服务和 Redis。虽然本地原型主要验证路由和鉴权能力，但 Gateway 的存在为后续生产级流量治理提供了明确扩展点。

因此，Gateway 在本项目中不仅是一个路由组件，也是统一认证、权限控制、入口治理和生产演进的关键基础设施。

## 10.7 本项目技术选型总结

本项目的技术选型围绕“高并发秒杀与智能电商后台”这一业务场景展开，各组件分别承担不同层次的系统职责。

Gateway 负责统一入口和权限控制，使所有客户端请求都经过一致的认证、路由和治理流程。MySQL 负责保存用户、商品、库存、活动、订单和消息日志等最终业务事实，是系统数据一致性的最终依据。Redis 负责秒杀库存、用户参与标记、秒杀结果和 AI 问答缓存等高频访问数据，适合承担瞬时高并发读写压力。RabbitMQ 负责将 Redis 扣减成功后的订单创建请求异步化，避免订单写入直接阻塞秒杀接口。SSE 负责在订单创建成功后向用户实时推送结果，提升用户对异步订单链路的感知。LLM API 则为系统提供智能导购能力，但需要通过缓存、限流、超时和降级机制控制调用成本和外部依赖风险。

从整体上看，本项目没有将所有业务都集中在单一服务或单一数据库中，而是根据不同技术的适用场景进行组合：Gateway 解决入口治理问题，Redis 解决高并发资格抢占问题，RabbitMQ 解决订单写入削峰问题，MySQL 解决最终持久化问题，SSE 解决实时反馈问题，AI 服务解决智能咨询问题。该技术组合既能满足本地原型验收，也能自然扩展到生产环境中的多实例部署、集群化中间件和可观测性治理。

## 11.3 用户认证与权限测试

用户认证与权限测试的目标是验证 Gateway 能否正确处理登录态、Token 校验和角色权限控制。测试首先通过普通用户注册和登录接口获取 CUSTOMER Token，再通过管理员登录接口获取 ADMIN Token。随后分别使用不同 Token 访问普通用户接口和管理员接口，观察系统是否按照权限设计返回正确结果。

测试内容包括以下几类：

1. 未携带 Token 访问 CUSTOMER 或 ADMIN 接口，应返回 401。
2. 携带无效或过期 Token 访问受保护接口，应返回 401。
3. 普通用户访问发起秒杀、查询个人订单、AI 咨询和建立推送连接接口，应访问成功。
4. 普通用户访问创建商品、设置库存、创建秒杀活动和管理员订单查询接口，应返回 403。
5. 管理员访问商品管理、库存配置和活动创建接口，应访问成功。
6. 所有认证失败和权限失败响应均应符合统一响应格式。

该测试能够验证用户模块、Gateway 和权限规范之间的一致性。若 Gateway 未正确执行权限判断，普通用户可能绕过角色限制调用管理员接口；若内部服务不信任 Gateway 注入上下文，也可能导致服务间权限口径不一致。因此，认证与权限测试是整个系统安全边界的基础验证。

## 11.9 测试结果分析

从系统验收角度看，测试结果应围绕“接口可访问、权限可控制、链路可闭环、状态可观察、异常可解释”五个方面进行分析。

首先，接口可访问体现在所有客户端请求均通过 Gateway 进入系统，Apifox 和测试页面的 Base URL 均为 `http://localhost:8080`。用户注册、登录、商品查询、秒杀活动查询、发起秒杀、订单查询、AI 咨询和推送连接等接口应能够按照权限要求正常访问。

其次，权限可控制体现在普通用户和管理员接口边界清晰。普通用户可以参与秒杀和查询个人订单，但不能创建商品、设置库存或创建秒杀活动；管理员可以执行管理类操作。未登录或 Token 无效时返回 401，权限不足时返回 403，且响应结构符合统一格式。

第三，链路可闭环体现在秒杀请求不是停留在接口返回层面，而是能够贯穿 Redis、RabbitMQ、order-service、MySQL 和 push-service。秒杀接口返回 QUEUEING 后，应能观察到 Redis 库存扣减、RabbitMQ 订单创建消息、订单服务消费日志、MySQL 中 CREATED 订单记录和用户侧推送结果。

第四，状态可观察体现在系统中的关键过程数据可通过中间件和数据库进行验证。Redis 中可观察 `seckill:stock:{activityId}`、`seckill:user:{activityId}:{userId}` 和 `seckill:result:{activityId}:{userId}`；RabbitMQ 中可观察订单创建队列；MySQL 中可查询订单主表、订单明细表和 MQ 消息日志表。

最后，异常可解释体现在库存不足、重复抢购、活动未开始、活动已结束、MQ 投递失败、AI 调用失败等场景均有明确错误码和处理策略。该特性对于课程验收和答辩尤为重要，因为系统不仅需要展示成功路径，也需要说明异常状态下的系统行为边界。

# 12 正式生产环境演进方案

## 12.1 本地原型与生产环境差异分析

本地原型主要用于验证课程要求中的核心技术链路，因此通常采用单机或轻量化部署形态。Gateway、各业务微服务、MySQL、Redis 和 RabbitMQ 在本地环境中多以单实例运行，重点验证系统是否具备统一入口、JWT 认证、高并发秒杀防超卖、RabbitMQ 异步订单削峰、SSE 实时推送和 AI 咨询等能力。

生产环境面对的约束与本地原型显著不同。首先，生产环境需要处理更高并发、更大数据量和更复杂的故障场景，任何单个服务或中间件实例都可能成为单点故障。其次，秒杀活动可能带来瞬时流量峰值，系统需要在入口层、缓存层、消息层和数据库层同时具备削峰和保护机制。再次，生产环境需要具备日志、指标、链路追踪和告警能力，否则难以及时定位接口错误、MQ 积压、Redis 异常或数据库瓶颈。

因此，本项目从本地原型向生产环境演进时，需要重点解决以下问题：Gateway 如何避免单点故障；业务微服务如何水平扩容；Redis 如何从单机演进为高可用集群；RabbitMQ 如何保证消息可靠性；MySQL 如何实现主从复制和读写分离；秒杀库存热点如何治理；AI 调用如何通过缓存、限流、排队和降级降低外部依赖风险；系统如何通过监控告警实现可观测和可运维。

## 12.2 生产环境总体架构设计

生产环境总体架构应在本地原型的基础上引入负载均衡、服务多实例、中间件集群和可观测性平台。客户端请求首先进入 Nginx 或云负载均衡，再分发至多个 Gateway 实例。Gateway 完成统一认证、权限判断、路由转发、限流和日志记录后，将请求转发到后端业务服务集群。

业务服务包括 user-service、product-seckill-service、order-service、push-service 和 ai-service，各服务均应尽量保持无状态化，以便根据流量进行水平扩容。服务状态不保存在本地实例内，而是沉淀到 MySQL、Redis 和 RabbitMQ 等共享基础设施中。

Redis 从单机演进为 Sentinel 或 Cluster，用于支撑秒杀库存、用户参与标记、秒杀结果和热点缓存。RabbitMQ 从单机演进为集群，并开启消息持久化、生产者确认、消费者 ACK、重试和死信队列。MySQL 从单机演进为主从复制和读写分离架构，写操作进入主库，查询类操作可进入从库。AI 调用链路则应引入缓存、限流、队列和降级，避免外部 LLM 服务影响秒杀和订单主链路。

## 12.3 Gateway 集群与负载均衡设计

在本地原型中，Gateway 以单实例运行，主要验证统一入口、路由转发和 JWT 鉴权能力。生产环境中，Gateway 不应成为单点故障。系统应在多个 Gateway 实例前部署 Nginx、云负载均衡或 SLB，由负载均衡组件将外部请求分发到不同 Gateway 实例。

Gateway 集群需要保持无状态化。用户登录状态不应存储在某个 Gateway 实例内，而应通过客户端携带 JWT Token 和后端统一校验实现。这样即使某个 Gateway 实例宕机，负载均衡也可以将请求转发到其他实例，用户无需感知具体实例变化。

生产环境中的 Gateway 职责应保持收敛，主要包括路由转发、认证鉴权、跨域处理、访问日志、限流、熔断和请求追踪 ID 注入。具体业务逻辑不应下沉到 Gateway，否则 Gateway 会随着业务增长而复杂化，影响系统可维护性。

在秒杀活动中，Gateway 还应承担入口限流职责。可以按 IP、用户 ID、接口路径、活动 ID 等维度设置限流规则，对明显异常或超出阈值的请求直接返回 429，避免无效流量继续进入商品秒杀服务和 Redis。

## 12.4 微服务多实例部署方案

生产环境中，user-service、product-seckill-service、order-service、push-service 和 ai-service 均应采用多实例部署。多实例部署的前提是业务服务尽量无状态化，即服务实例本身不保存必须依赖本机内存的用户会话、订单状态或秒杀状态，而是将状态存储在 MySQL、Redis 或 RabbitMQ 中。

user-service 可以根据登录和用户查询流量进行水平扩容。product-seckill-service 是秒杀活动开始时的主要流量入口，应根据 QPS、CPU 使用率和 Redis 调用耗时进行扩容。order-service 的扩容依据不仅包括 CPU 和内存，也包括 RabbitMQ 队列积压长度。当订单创建消息积压增加时，可以增加 order-service 消费实例，提高消息处理能力。

push-service 需要维护 SSE 长连接，生产环境中应重点考虑连接数、心跳、断线重连和用户连接路由问题。ai-service 则应与秒杀和订单主链路隔离部署，即使 LLM API 故障或 AI 服务高负载，也不应影响用户发起秒杀和查询订单。

多实例部署还需要配合配置管理、健康检查和滚动发布机制。服务启动后应暴露健康检查接口，负载均衡或服务治理组件仅将流量转发到健康实例。版本更新时，应通过滚动发布逐步替换旧实例，避免系统整体不可用。

## 12.13 日志、监控、链路追踪与告警设计

生产环境中，系统不仅需要能够处理请求，还需要能够观察请求在系统中的流转过程。没有完善的日志、监控、链路追踪和告警机制，即使系统在本地原型中能够跑通，也难以及时发现生产环境中的性能瓶颈和故障风险。

日志方面，Gateway 应记录请求入口、请求路径、用户标识、角色、响应状态、耗时和追踪 ID。业务服务应记录关键业务事件，例如用户登录、创建商品、创建秒杀活动、Redis 扣减结果、MQ 投递结果、订单消费结果、推送结果和 AI 调用结果。日志中不得输出真实密码、完整 Token、LLM API Key 等敏感信息。

监控方面，系统应至少关注以下指标：Gateway QPS、接口错误率、接口平均响应时间和 P95/P99 响应时间；Redis 命令耗时、库存 Key 异常、缓存命中率；RabbitMQ 队列积压长度、消息消费速率、死信队列数量；MySQL 慢 SQL、连接数、主从延迟；AI 服务调用耗时、缓存命中率、失败率和降级率。

链路追踪方面，Gateway 可在请求进入时生成统一的 traceId，并将其传递给后续业务服务。一次秒杀请求可能经过 Gateway、product-seckill-service、Redis、RabbitMQ、order-service、MySQL 和 push-service，链路追踪可以帮助定位请求在哪个环节耗时过长或发生异常。

告警方面，系统应针对关键异常设置阈值。例如，当 Gateway 5xx 错误率超过阈值、RabbitMQ 订单队列积压持续增长、Redis 秒杀库存出现异常、MySQL 主从延迟过高、AI 调用失败率显著上升或死信队列出现大量消息时，应及时触发告警，通知运维或开发人员处理。

通过日志、监控、链路追踪和告警体系，生产环境中的高并发秒杀链路才能从“功能可运行”进一步提升为“状态可观察、故障可定位、风险可预警”的工程系统。

## 13.1 项目完成情况总结

本项目围绕 AI 驱动的高并发秒杀与智能电商后台系统，完成了从需求分析、架构设计、接口契约、核心链路实现到测试验收和生产演进分析的整体设计。系统采用微服务原型架构，通过 gateway-service、user-service、product-seckill-service、order-service、push-service 和 ai-service 等服务划分，实现了用户认证、商品管理、秒杀活动、异步订单、实时推送和 AI 咨询等功能。

在核心架构能力方面，系统通过 Gateway 实现统一入口和权限控制；通过 Redis 预热秒杀库存并使用 Lua 脚本完成原子扣减；通过 RabbitMQ 将订单创建请求异步化，降低数据库瞬时写入压力；通过 MySQL 保存最终业务事实；通过 SSE 向用户实时推送订单创建结果；通过 AI 服务接入大语言模型能力，并提供缓存和降级策略。

在文档与测试方面，项目维护了总体架构设计、接口契约、统一响应格式、认证权限规范、数据库设计、Redis Key 设计、MQ 消息契约、部署启动指南和演示链路说明等文档，为代码实现、Apifox 联调和最终报告提供统一依据。

## 13.2 系统优势总结

本系统的主要优势体现在以下几个方面。

第一，系统入口统一。所有客户端请求均通过 Gateway 进入，认证、权限、路由和后续限流治理均可在统一位置处理，避免多个业务服务重复实现入口逻辑。

第二，秒杀链路具备清晰的高并发处理方案。系统不直接使用数据库扣减秒杀库存，而是通过 Redis 预热库存和 Lua 原子扣减处理高频请求，从架构上降低数据库压力并减少超卖风险。

第三，订单创建采用异步削峰模式。Redis 扣减成功后，系统通过 RabbitMQ 将订单创建任务排队，由订单服务按自身处理能力消费并写入 MySQL，使秒杀接口能够快速返回 QUEUEING。

第四，系统状态具有可解释性。QUEUEING、CREATED、FAILED 等状态区分清晰，Redis、RabbitMQ 和 MySQL 中均可观察到对应过程数据，便于测试和验收。

第五，AI 能力接入方式较稳健。系统没有将 AI 调用放入秒杀主链路，也没有在 LLM 失败时伪造成功结果，而是通过缓存、超时和降级机制控制外部依赖风险。

## 13.3 当前不足分析

本项目作为课程本地原型，仍存在一些不足。

首先，本地部署以单实例为主，虽然报告中给出了生产环境演进方案，但尚未真实部署 Gateway 集群、Redis Cluster、RabbitMQ 集群和 MySQL 主从架构，因此高可用能力主要体现在设计层面。

其次，秒杀并发测试规模受本地机器性能限制，无法完全模拟真实百万日活或大规模公有云环境下的流量波动。当前测试更适合验证设计正确性，而不是代表生产环境极限性能。

第三，AI 智能导购模块仍以基础商品上下文和问答缓存为主，尚未引入更复杂的相似问题召回、向量检索、用户画像和流式响应能力。

第四，系统可观测性仍有提升空间。本地原型主要依赖日志、Apifox、Redis、RabbitMQ 管理台和数据库查询进行验证，尚未完整接入统一指标平台、链路追踪系统和自动告警系统。

## 13.4 后续改进方向

后续可以从生产化、性能优化和智能化三个方向继续改进本项目。

在生产化方面，可以引入服务注册与发现、配置中心、统一日志平台、链路追踪和监控告警系统，并将 Gateway、业务服务、Redis、RabbitMQ 和 MySQL 按照生产环境方案进行集群化部署验证。

在性能优化方面，可以进一步实现 Gateway 层限流、秒杀库存分片、热点商品缓存、订单服务动态扩容、MQ 消息补偿任务和数据库读写分离，提升系统面对流量突增时的稳定性。

在智能化方面，可以扩展 AI 商品咨询能力，引入相似问题检索、热门问答缓存、用户级限流、请求排队和流式响应，使 AI 服务在高并发场景下更加可控，并提供更好的用户交互体验。

总体而言，本项目完成了从本地可运行原型到生产环境演进方案的完整设计，能够体现现代 Web 后端系统在高并发处理、异步架构、实时通信和 AI 集成方面的核心设计思想。
